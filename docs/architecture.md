# 架构

本文规定实现机制。可见行为以 [product.md](product.md) 为准。模块路径如下，分成已经接入和尚未接入。

## 技术验证

通过标准、记录要求和各项结论见 [roadmap.md](roadmap.md)「技术验证」。某项没有通过记录之前，不写依赖它的界面代码。某项失败时，先改本文的方案，必要时再改产品规格，不在功能代码里绕过。技术验证里的测量只说明该场景，不算「性能测量」一节的验收。

## 运行时

- 只支持 Windows 11 x64。
- 界面用 Slint。渲染器默认 FemtoVG。初始化失败时自动退回软件渲染。外壳先 `BackendSelector::renderer_name("femtovg")`。这次 `select` 失败再用 `"software"`。不启用 Skia，因此窗口适配器的退路里也没有 Skia。`select` 成功之后，若 FemtoVG 在创建窗口适配器时失败（例如探测不到 OpenGL 2），Slint 1.18.1 的 winit 后端会再试已编译的渲染器，其中包含软件渲染。窗口已经显示之后，这一版不能再从 FemtoVG 换到软件渲染。窗口外观用 Desktop Window Manager：无边框、圆角、暗色。搜索条和面板的亚克力是 `DWMWA_SYSTEMBACKDROP_TYPE` 的 transient backdrop。展开的悬浮窗在透明可用时不用这一种，见「便签页与悬浮窗」的「背景」。透明不可用时用纯色背景。不做 CSS `backdrop-filter`，也不提供按百分比调节的玻璃透明度。技术验证的渲染器一项仍未通过，这里的默认不是那一项的通过记录。悬浮窗改用失焦后仍在的亚克力，也不改变「背景」和「渲染器」的通过记录。
- Slint crate 固定为 1.18.1。升级单独提交，并重跑依赖该版本行为的技术验证。
- `DWMWA_SYSTEMBACKDROP_TYPE` 从 Windows 11 Build 22621 起可用。运行时检查 build 和调用返回值，不可用时不设置该属性，按纯色处理。产品支持的最低 build 尚未确定。
- 进程内没有 Vue、Tauri、WebView2。
- Slint 按 Royalty-free 许可证 2.0 使用。固定文本是 tag `v1.18.1` 的 `LICENSES/LicenseRef-Slint-Royalty-free-2.0.md`，副本在 `third_party/slint/`。归属走许可证第 2 节 (b)：在可以下载二进制的公开网页上放 Slint 徽标 `MadeWithSlint-logo-whitebg.png`（同一 tag 的 `logo/`，副本在 `third_party/slint/`），并链到 <https://slint.dev>。界面里不放 `AboutSlint`。仓库已经公开。GitHub Release 按公开发布。未登录浏览器打开 Release 页、确认徽标和链接可见的记录还没有，那是第一次发布之后的人工步骤。
- 界面调用薄命令。命令做校验，业务规则在服务中。需要保存的数据先原子写入，成功后再向本进程已打开的窗口发变更消息。非法输入返回明确错误。单进程、单写者。
- 中文输入法能在搜索条、待办标题和便签正文中上屏。做不到这一点时，界面方案不成立，不能改用「只支持英文」通过验收。
- 搜索条和面板在启动时创建并保持隐藏，以满足热召回目标；隐藏中不做整页重绘。快速收集是搜索条的一种输入状态（仅便签收集 `/note` 仍计划中，待办快速收集已放弃），不另建窗口。便签悬浮窗、番茄钟在使用时创建，关闭时释放文本、图标和绘图资源。待办悬浮窗同样是使用时创建、关闭时释放，见「待办悬浮窗」。到期提醒的调度保留在主进程里。
- Slint 1.18.1 编进本仓库的 winit 后端没有实现 `start_drag`（`i-slint-backend-winit` 1.18.1 的 `WinitWindowAdapter` 只实现了 `start_window_move`；`WindowAdapterInternal::start_drag` 的默认实现返回 false）。因此 `DragArea` 的拖动留在窗口内。早期外部拖放技术验证用 `dispatch_event` 观察到：同一窗口里文件路径以复制放下，目标要求移动时放下被拒绝。winit 0.30.13 创建窗口时调用 `OleInitialize` 并 `RegisterDragDrop` 注册自己的 `FileDropHandler`；探针在我们注册之前得到 already-registered。资源管理器方向的手测见 [roadmap.md](roadmap.md)。`--slint` 拖放没有路径，外部拖放按「收纳」的原生 OLE 实现。
- 托盘用 Slint 1.18.1 的 `SystemTrayIcon`。它有菜单，图标是一张图，逾期数字画在这张图的右下角。因此没有改用 Win32 `Shell_NotifyIcon`。
- 热角检测用 50ms 轮询读取光标位置，不用低级鼠标钩子。机制、全屏抑制、按住左键时不触发和待定项见「热角」。产品不依赖 `spikes/hotcorner`。
- `spikes/hotcorner` 的实测结论见 [roadmap.md](roadmap.md)「技术验证」。那是 spike，不是 `lanwork.exe` 的验收。

Slint 负责版式。待办规则、便签保存、收纳、搜索索引不写进界面回调里。

## 程序外壳

模块分成两处。`lanwork_core::config` 和 `lanwork_core::shell` 不依赖 Slint，也不调用 Win32。互斥量、热键、注册表和窗口在 `crates/app`。非 Windows 进程打印「Lanwork 只支持 Windows 11 x64」并退出，退出码 1。

发布版 `lanwork.exe` 的 PE 子系统是 2（`IMAGE_SUBSYSTEM_WINDOWS_GUI`）。`crates/app/src/main.rs` 在 Windows 且没有 `debug_assertions` 时写 `windows_subsystem = "windows"`。`cargo build --release` 默认关掉 `debug_assertions`，安装包和便携版里的就是这个 GUI 程序。双击或从开始菜单启动时 Windows 不分配控制台，关掉一个控制台窗口也不会结束进程。调试构建不写这个属性，仍是控制台子系统，`cargo run` 能看到标准错误。日志在数据目录的 `logs/app.log`，不写到控制台。存储已经打开时，启动失败调用 `Store::log_error`；panic 也写入同一份日志。存储还没打开、但数据目录已经能解析、且目录不是 MayDolist 时，启动失败直接写 `logs/app.log`。`eprintln` 只是调试控制台的副本，发布版没有控制台接收它。数据目录解析失败时还没有日志文件，发布版也不弹出控制台，没有对话框。

启动顺序：先取得单实例，再解析数据目录并打开存储，然后完成存储启动、加载配置、按本地日期调用 `BackupCommands::backup_on_launch`、选择渲染器、注册热键、按配置写开机启动项，最后创建隐藏的搜索条、面板宿主和托盘，再按 `hotCorner` 启动热角轮询，安排检查更新，并安装到期提醒调度。安装版在平台线程用 `REGCLS_SUSPENDED` 注册通知激活，界面循环起来之后再 `CoResumeClassObjects`。这个窗口还收 `WM_POWERBROADCAST` 的恢复和 `WM_TIMECHANGE`，见「通知」。存储启动时外壳先注册 `BackupCommands` 的导入恢复钩子，再注册待办的加载和修复。存储启动之后打开 `NoteCommands`、`AppIndex::open_from_process`（随后用 `load_user_catalog` 读 `user-apps.json` 交给 `set_user_catalog`）和 `FileCommands`，组成 `Dispatch` 并 `build`。这几步任一失败只写日志，进程继续，搜索条不安装，按热键不出现。同一时刻打开 `ShelfCommands` 并调用 `watch_todo_notices`，待办被永久删除时分组的关联由它解除；打不开时只写日志，收纳页显示错误。旧 `config.json` 里的 `githubRefreshIntervalMs`、`staleDays`、`sourceSync`、`autoCompleteOnClose` 读取时忽略，不报错，也不隔离文件；写回时不再写这些字段。

- **单实例。** 命名互斥量 `Local\Lanwork.SingleInstance.Mutex`，加上信号量 `Local\Lanwork.SingleInstance.Activate`（初值 0）。第一个进程拥有互斥量并等待信号量。后来的进程发现互斥量已存在，就对信号量加一，然后退出，退出码 0。信号量的计数会留到第一个进程来取，所以通知发生在等待之前也不会丢。第一个进程收到通知后不打开窗口。产品规格没有写这时要显示什么。
- **应用图标。** 源文件是 `crates/app/assets/lanwork.svg`，按给出的字节原样放进仓库，不改花瓣，也不改颜色。同目录的 `lanwork-256.png` 是这张图的 256×256 渲染，同样原样提交。16、20、24、32、40、48、64 的 PNG，托盘底图 `lanwork-32.rgba`，以及含这八个尺寸的 `lanwork.ico`，由 `tools/render_app_icon.py` 从这张 256px 图做整数面积平均得到。脚本只用 Python 标准库，不重新解释 SVG。产物提交在仓库里。构建不运行这个脚本，也不需要 SVG 工具。Windows 目标上，`crates/app/build.rs` 用 `winresource` 把 `lanwork.ico` 编成资源 ID 1，链进 `lanwork.exe`，资源管理器和任务栏用它。同一份资源写入版本信息：字符串 `FileVersion` 和 `ProductVersion` 取 Cargo 包版本，当前是 `0.3.1`。数值 `FILEVERSION` 和 `PRODUCTVERSION` 是 Windows 要求的四段整数 `0.3.1.0`，对应这个 `0.3.1`，不是另一个版本。`ProductName` 和 `FileDescription` 写 `Lanwork`。非 Windows 目标不嵌入。搜索条、面板、便签悬浮窗和收纳悬浮窗的 Slint `Window` `icon` 用 `lanwork-256.png`。技术验证的「背景」和「渲染器」仍没有通过记录，给这些窗口设图标不改变那两项。
- **托盘。** 菜单顺序是「打开面板」「设置」「新建便签」「退出」。提示文字只有「Lanwork」。图标是 32×32 的应用图标。逾期数量来自 `TodoCommands::overdue_count`，今天的日期用 `GetLocalTime`。数量为 0 时不画数字。数量不为 0 时在右下角盖一块徽章再画原来的 5×7 数字：白底、深色笔画、一圈深色边。一位和两位按 2 倍笔画，更长时按 1 倍。画不出图标的笔画裁掉，不改成「99+」。徽章的底色、边和放大倍数是实现选择，产品规格没有写徽章的样子。有新版本时另在右上角画一个小点，颜色和大小是实现选择，不盖住右下角的逾期徽章。重画逾期数量时小点留着。待办变更消息到达后在界面线程重画。到期提醒每次计算时也重画，见「通知」。读数量或日期失败时不画数字，并写日志。左键和右键都由 Slint 打开同一份菜单，没有另加左键动作。
- **打开面板、设置、新建便签。** 「打开面板」显示面板，标签保持收起前的选择。「设置」显示面板并切到设置标签，见「设置页」。「新建便签」创建一篇空便签，显示面板并切到便签页，选中它；没有便签服务时只显示错误。当前编辑区有没写盘的修改且保存失败时，先停在原来的便签上，等用户重试或放弃。
- **退出。** 先保存面板便签页和所有悬浮窗里没写盘的修改，并记下仍打开的悬浮窗的位置和大小。`quit_decision(unsaved)` 在仍有没写盘的修改时返回 `QuitDecision::Stay`：不结束进程，显示出相关窗口，窗口上有「重试」和「放弃修改」；重试成功、放弃或选定冲突版本之后再继续退出：这些动作发生在窗口自己的回调里，面板和悬浮窗的表还被借用着，所以 `continue_quit` 只登记，下一轮事件循环才再次尝试（`lanwork_core::shell::resume_quit_later`）。全部写盘后，如果已经有核对过的安装包，先启动安装助手；助手起不来就不退出，设置页显示「安装失败」。否则隐藏托盘、退出事件循环。事件循环退出后，设置页若还在录入热键，先走录入的唯一出口（见「设置页」），然后卸下热键并释放互斥量。安装助手见「更新」。
- **热键。** `RegisterHotKey` 带 `MOD_NOREPEAT`，注册在单独线程的一个不显示的顶层窗口上。这个窗口不带 `WS_VISIBLE`。不用 `HWND_MESSAGE`，否则收不到 `WM_SETTINGCHANGE`。单一热键注册，仅注册搜索条热键（原预留的面板热键已从规格中放弃，不再注册），id 只是某一次注册的句柄：`RegisterHotKey` 在同一窗口、同一 id 上再注册一次时，旧组合不会被替换，两个组合会同时有效（微软文档写明，只有 Windows Server 2003 才是替换），所以换组合时用一个新 id 注册，旧 id 在写盘成功之后才 `UnregisterHotKey`；`WM_HOTKEY` 到达时用 id 查当前注册表得到角色，查不到的 id（已卸掉的）不处理。字符串格式沿用原来的写法：修饰键 `Ctrl`、`Alt`、`Shift`、`Win`，加一个主键，比较和保存前收成 `Ctrl+Alt+Shift+Win+键`。大小写不区分，`+` 两侧空白会去掉。主键文本是 `A`–`Z`、`0`–`9`、`F1`–`F24`、`Space`、`Up`、`Down`、`Left`、`Right`、`Home`、`End`、`PageUp`、`PageDown`、`Insert`、`Delete`、标点 `;`、`=`、`,`、`-`、`.`、`/`、反引号、`[`、`\`、`]`、`'`、`Numpad0`–`Numpad9`、`NumpadMultiply`、`NumpadAdd`、`NumpadSubtract`、`NumpadDivide`。这些名字和 Win32 虚拟键码一一对应，能和原来的 `Ctrl+Alt+M`、`F1`、`Ctrl+0` 互转。`+` 是分隔符，小键盘加号写成 `NumpadAdd`，不写成 `+`。除 `F1`–`F24` 外必须至少有一个修饰键，单独的普通键是「热键无效」。`F1`–`F24` 可以没有修饰键。不在这张表里的键名也是「热键无效」。录入、保存和解析用同一套规则。不另设占用黑名单，注册失败仍是「热键已被占用」。`WM_HOTKEY` 只有修饰键和虚拟键码，没有扩展位。NumLock 关闭时，小键盘数字和对应的导航键是同一个虚拟键码，触发时分不开：存成 `Numpad4` 的热键不会响，存成 `Left` 的热键也会被小键盘 4 触发。小键盘 0–3、6–9 和 Insert、End、Down、PageDown、Right、Home、Up、PageUp 同样如此。小键盘 5 在 NumLock 关闭时是 `VK_CLEAR`，存成 `Numpad5` 的热键不会响。这是 `RegisterHotKey` 的限制。搜索条热键为空是「搜索条热键不能为空」。运行中修改热键只走先注册、成功后写入配置、再卸掉不再使用的旧热键。注册失败时磁盘和当前注册都保持旧热键。内容没变时不调用系统。写入配置时先更新内存，再发布变更。设置页录入搜索条热键时的做法见「设置页」。第一次启动就占用时，不改 `config.json`，写日志，进程继续，搜索条热键保持未注册。没注册上的热键记在设置页状态里（`HotkeyRecording`），面板错误条显示「搜索条热键已被占用」，面板打开时就显示，收起不清，之后注册上才清。搜索条热键显示或收起搜索条，见下面的「搜索条」。
- **配置。** 见「数据」。不认识的 `schemaVersion` 让进程以退出码 1 结束，不改文件，没有对话框。
- **主题。** 明和暗直接写调色板。跟随系统时读 `HKCU\Software\Microsoft\Windows\CurrentVersion\Themes\Personalize` 的 `AppsUseLightTheme`：0 是暗，其他值是明。读不到就不改调色板，也不猜测。`WM_SETTINGCHANGE` 且 `lParam` 为 `ImmersiveColorSet`（忽略 ASCII 大小写）时再读一次。调色板用 `ColorScheme.dark` 和 `ColorScheme.light` 这两个变体名。Slint 1.18.1 里这两个变体的注释文字和名字相反，以变体名为准。
- **开机启动。** `HKCU\Software\Microsoft\Windows\CurrentVersion\Run` 的值名 `Lanwork`，类型 `REG_SZ`，内容是带引号的 exe 路径。配置为真且与现有值不同就写；为假且值存在就删。路径为空、不是 Unicode 或含 `"` 时不写。写入或删除失败只记日志，不把配置里的开关改回去。读不到现有值时也不改注册表。设置页切换开关时同样先写 `config.json`，再调用这一套写或删；注册表失败时配置保持新值，界面显示错误，见「设置页」。
- **隐藏窗口。** 搜索条和面板在 `Component::new` 时创建，不调用 `show`。Slint 1.18.1 在这时创建 winit 适配器并登记为未激活窗口，事件循环开始时创建不可见的操作系统窗口，不会把未显示的窗口设为可见。面板同样先隐藏，背景在每次显示前判断。事件循环用 `run_event_loop_until_quit`：搜索条收起后所有窗口都隐藏，事件循环不能因此结束；托盘「退出」才结束。

外壳在 `boot` 前注册 `BackupCommands::register_boot_hooks`。有 `import.pending` 时先恢复，再加载待办和配置。`import_recovered` 为真时记日志「导入未完成」，并留在 `import_was_recovered`。界面尚未显示这句提示。读不到本地日期或自动备份失败时记日志，进程继续。没有恢复钩子时 `boot` 仍失败，外壳以退出码 1 结束。

### 搜索条

可见行为见产品规格「搜索条」「搜索」。代码在 `crates/app/src/searchbar.rs`（窗口与调度）、`crates/app/src/bar_win.rs`（Win32）和 `crates/app/ui/searchbar.slint`（版式）。不调用 Win32 的决定在 `lanwork_core::shell` 的 `bar`：背景选择、位置（含记住的位置这次能不能用）、修饰键与动作、Esc、收起后保留的文本、选择移动和结果区那一行文字。

技术验证的「背景」和「渲染器」两项仍没有通过记录。这一版搜索条的界面代码依赖这两项，写在通过之前；两项的记录不因此改变。

- **窗口。** `no-frame`，逻辑宽 680px，高度是输入框 56px 加结果区。结果行 48px，换组时多留 10px 并画一条分隔线，列表上下各留 6px。结果区最多约 9 行高，并且从窗口实际 y 收到所在显示器工作区底边之上 24px，见「位置」；更多的行在 `Flickable` 里滚动。版式数值是实现选择，产品规格没有写。字体 `Microsoft YaHei UI`。高度变化由 winit 改窗口大小，左上角不动。没有记住位置时上边缘留在 25% 处；记住位置后留在记住的那一点。拖动的模态循环进行中不改列表高度，松手后才重算。winit 无边框窗口的样式总带 `WS_CAPTION | WS_SYSMENU`，按标志再加最小化、最大化框；边框扩展到整个客户区后，DWM 会在右上角画出这三个按钮。winit 每次改可见性都按自己的标志重写 `GWL_STYLE`，所以窗口第一次存在时用 `SetWindowSubclass` 装一个子类：处理 `WM_STYLECHANGING` 时从新样式里去掉 `WS_SYSMENU | WS_MINIMIZEBOX | WS_MAXIMIZEBOX`，并立即对当前样式去一次再 `SWP_FRAMECHANGED`。`WS_CAPTION` 保留，DWM 仍画阴影和圆角。子类在 `WM_NCDESTROY` 时移除。
- **结果行。** 名称拆成三段交给 Slint，中间一段用粗体：`lanwork_core::shell::match_span` 在显示名里找输入（去掉首尾空白）的第一处，逐字符比较，小写恰好是一个字符时按小写比，否则按原字符。找不到时整段用常规字重。文件和文件夹行（`location_always_shown`）在名称下方总是显示 `location`，也就是完整路径；其它行选中且 `location` 非空时才显示。
- **Alt+数字。** `key-pressed` 在预编辑检查之后、Enter 之前处理：只按着 Alt（没有 Ctrl、Shift、Win），并且 `event.text` 是一个 1 至 9 的数字字符时调用 `shortcut`。`Flickable` 的 `content-y` 变化时把滚动量交给 Rust。`lanwork_core::shell::shortcut_rows` 用各行的 `y`、滚动量和结果区高度算出完整露出的行，从第一条起取至多 9 条连续的行；界面据此在行右侧画「Alt+N」，类型文字左移。`shortcut_target` 把数字换成行号，然后选中该行，按不带修饰键的 Enter 处理，所以组合输入、收集前缀和过期序号下同样无效。winit 处理 `WM_SYSCHAR` 时返回 0，不交给 `DefWindowProc`，所以 Alt+数字不会走到 `SC_KEYMENU`；没有菜单时是否仍有提示音，要在 Windows 上确认。
- **位置。** 没有记住位置时，每次显示前用 `GetCursorPos`、`MonitorFromPoint`、`GetMonitorInfoW` 的 `rcWork` 和 `GetDpiForMonitor(MDT_EFFECTIVE_DPI)` 算出物理坐标：水平居中，上边缘在工作区高度 25% 处，再 `set_position`。显示后用 `GetWindowRect` 再对一次，不一致时 `SetWindowPos`（不改大小、不激活）。记住的位置在 `config.json` 的 `searchBarOrigin`（`x`、`y`）。没有这个字段的旧配置按没有记住处理，仍用上面的默认位置。有记住的位置、并且下面的临时判断认为它还在某块显示器上时，显示前把窗口左上角设到这个坐标，不再跟光标走。结果列表的最大高度取两数里较小的一个：从窗口实际左上角的 y 到该点所在显示器的 `rcWork.bottom`，按那块屏的 DPI 换成逻辑像素，再减去输入行 56px 和底边留白 24px；以及约 9 行（9×48px，再加列表上下各 6px）。默认位置的 y 就是工作区高度 25% 处，显示器是光标所在的那块。换算按四舍五入，多出来的逻辑像素会减掉，使输入行、列表和 24px 留白的物理高度不超过 `bottom − y`。每次显示时按这次要放到的 y 计算；拖动结束时按 `GetWindowRect` 的 y 再算一次。这个点不在任何 `rcMonitor` 内时，这次不改已经算出的高度。
- **拖动。** 产品规格写了可以拖动并记住位置，没有写从哪里拖。临时做法，不是产品规则：只在输入行左侧、输入框左边的一条上按下左键后调用 winit 的 `drag_window`。这条的逻辑宽度是 52px（与版式里输入框的 `x` 相同），高度等于输入行。不覆盖 `TextInput`，也不覆盖结果行的 `TouchArea`，所以在输入框里拖选文字、结果悬停和单击都不走到拖动。`drag_window` 在 Windows 上是 `ReleaseCapture` 再投递 `WM_NCLBUTTONDOWN` / `HTCAPTION`，真正的移动在之后的模态循环里。`WM_ENTERSIZEMOVE` 到 `WM_EXITSIZEMOVE` 算作拖动中，这段时间里的失焦不收起；循环结束后再留两轮事件循环，躲开拖动结束时迟到的 `Focused(false)`，然后把焦点还给输入框。循环结束时按 `GetWindowRect` 的 y 重算结果列表最大高度，并把左上角写入配置；与按下时相同，或与已记住的相同，则不写。只点一下拖动条、窗口没动，不会把当次的默认位置记下来。写盘失败时原文件保持，搜索条状态行显示错误。进程在循环还没结束时被杀掉，这次的位置不写入。
- **待定，下面都不是产品规则。** 从哪里拖，见上一条的临时做法。按绝对坐标还是按当前屏幕记，没有选定：临时记下的是虚拟屏幕绝对物理像素（`GetWindowRect` 的 left/top），不记录是哪块屏幕，也不换成相对那块屏幕的偏移；多块显示器的矩形重叠时，用枚举到的第一块。屏幕变化，或记住的位置不在任何显示器内，没有选定：临时只看左上角这一点是否落在某块显示器的 `rcMonitor` 内（左闭右开、上闭下开）。不落在任何一块内时，这次显示退回默认位置，不改写已经记住的坐标，也不把窗口拉进最近的显示器。屏幕变了但这个点仍落在某块显示器上时，仍用记住的绝对坐标，不按新布局重算。是否提供恢复默认位置，没有选定：现在没有按钮、菜单或热键；把窗口拖回默认坐标那个点，配置里仍留着坐标，不算清除。是否受 DPI 影响，没有选定：临时不按 DPI 换算记住的坐标，显示时原样 `set_position`。默认位置仍按光标所在显示器的 DPI 把逻辑宽度换成物理像素后再居中。列表高度的 DPI 用的是包含该点的那块显示器的有效 DPI，读不到时用 96。窗口拖到接近工作区底边、剩下的距离放不下输入行加 24px 时怎么办，没有选定：临时把结果列表的最大高度设为 0，列表不显示，不移动窗口，也不缩短输入行。输入行本身越过 `rcWork.bottom` 之上 24px 时仍停在拖到的位置，可能伸出工作区。拖动的模态循环里高度不跟着光标变，松手后才重算。结果区里分隔线 1px 和状态行 36px 没有算进这个上限；状态行出现时，窗口底边仍可能越过工作区底边再减去 24px 的那条线。
- **背景。** 窗口第一次存在（`winit_window()` 完成）时、每次显示前、主题变化时重新判断。Windows build 低于 22621 或读不到、`EnableTransparency` 为 0 或读不到（值不存在按开启）、`GetSystemPowerStatus` 报节电或读不到时用纯色。否则 `DwmExtendFrameIntoClientArea(-1)`，再设 `DWMWA_SYSTEMBACKDROP_TYPE = DWMSBT_TRANSIENTWINDOW`；任一调用失败也用纯色。纯色时仍扩展边框，并把背景类型设回 `DWMSBT_NONE`，客户区由 Slint 画满 `#F3F3F3`（浅）或 `#202020`（暗）。圆角是 `DWMWCP_ROUND`，暗色用 `DWMWA_USE_IMMERSIVE_DARK_MODE`。透明渲染本身失败（例如客户区画成黑色）没有在运行时检测，只看 DWM 调用的返回值。`DWMSBT_TRANSIENTWINDOW` 在窗口失活时会被系统收成不透明。搜索条和面板失焦就收起，看不见那一下。展开的悬浮窗失焦后仍留在屏幕上，不用这一条，见「便签页与悬浮窗」的「背景」。
- **任务栏。** 用 `unstable-winit-030` 的 `set_skip_taskbar(true)`，由 winit 在样式更新时保留。不手写 `WS_EX_TOOLWINDOW`，winit 每次改窗口状态都会重写扩展样式。
- **显示与收起。** 热键在搜索条可见时收起，否则显示：定位（见「位置」）、设背景、`show`、`bring_to_front`（见「面板」的「前台」）、焦点给输入框。`GetForegroundWindow` 对不上这个窗口时收起并清掉可见状态，记一条警告，避免停在已显示。规格没有写搜索条拿不到前台时怎么办，待定。winit 的 `Focused(false)` 到达时收起；拖动过程中的失焦不收起，见「拖动」。收起时除未提交的收集文本外清空输入并向调度提交空串，然后把延迟记录写出。
- **输入。** 输入框是 `TextInput`，不是 `LineEdit`，因为要读 `preedit-text`。`key-pressed` 里预编辑非空时一律交还输入法。Esc、上、下、Enter 由搜索条处理，其他键交给 `TextInput`。`edited` 把已提交的文本交给 `Dispatch::submit(Surface::SearchBar, …)`，结果在界面线程上立即画出。以 `/note` 开头的收集前缀时调度返回收集状态，搜索条不显示结果；便签收集预览和提交还没有接入（待办快速收集已放弃）。
- **后台。** 一个线程取当前可见行的图标；文件阶段还在等待时，等 60ms（新输入重新计时）再 `poll`，结果和图标交回界面线程。界面只接受 `accepts` 为真的序号。同一段输入的后续结果保留选中的那一条，输入变了回到第一条。上下键不回绕。每行有一个 `TouchArea`：指针在行上移动（`PointerEventKind.move`）时选中该行，列表在静止的指针下滚动不改选择；单击先选中该行，再按不带修饰键的 Enter 处理，组合输入期间同样无效。滚轮交给 `Flickable`。
- **动作。** 由 `row_action` 决定，没有动作时按键无效。Shell 调用在单独线程上，成功后收起，失败时在结果区下方显示错误并写日志，不收起；那时已经因失焦收起的只写日志。打开一项（不含打开所在目录和网页搜索）后 `record_open`。网页搜索行把 `RowDetail::WebSearch` 里的地址作为 `LaunchTarget::Url` 交给 Shell，由默认浏览器打开。「打开网址」把 `RowDetail::Browser` 里的地址同样交给 Shell，由默认浏览器打开，并 `record_open`。待办和便签结果先 `record_open` 再收起。待办结果随后调用 `panel::open_target`，面板打开并定位（见「面板」）；便签结果 Enter 调用 `panel::open_target(PanelTarget::Note { .. })`，Ctrl+Enter 调用 `note_float::open`，悬浮失败时在面板上显示错误。
- **延迟记录。** 环境变量 `LANWORK_LATENCY_OUT` 非空时，热召回和结果延迟的原始记录按 `tools/README.md` 的 JSONL 追加到该文件。界面不暴露这个变量。热召回起点是平台线程收到 `WM_HOTKEY` 时的 `SystemClock`，终点是显示后第一次 `AfterRendering`。结果记录在同一序号的视图画出后用 `mark_rendered` 填终点：本地结果在第一次画出时，文件来源在文件阶段结束的视图画出时。进程启动后第一次热召回和第一个查询序号标为预热。已经填了终点的记录不再因后来的输入标为被取代。没有按「性能测量」采样时，这些记录不表示目标已经达到。

### 面板

可见行为见产品规格「面板」「待办」。代码在 `crates/app/src/panel.rs`（窗口与调用）和 `crates/app/ui/panel.slint`（版式）。不调用窗口 API 的决定在 `lanwork_core::panel`：标签顺序、窗口尺寸与位置、待办页的清单和行、定位、排序换位、到期日与提醒的输入解析，以及设置页的热角选项和「先写配置、成功后才生效」的顺序（`panel::settings_page`）。

技术验证的「背景」和「渲染器」两项仍没有通过记录。面板的界面代码依赖这两项，写在通过之前；两项的记录不因此改变。窗口外观沿用搜索条的做法：`no-frame`，`bar_win` 里的子类去掉标题栏按钮，DWM 圆角与暗色，亚克力或纯色回退，主题变化时重新判断，任务栏不显示。

- **已有。** 标题栏（产品名、四个标签、关闭）、待办页、便签页、收纳页、设置页（见「设置页」：开机启动、热角、搜索条热键、检查更新，以及「隐藏的应用」）。待办行和字段区有收纳标记和「打开关联收纳」。托盘「打开面板」「设置」、搜索条的待办结果和热角会打开面板。关闭按钮、失焦和 Esc 收起，不退出进程；收起后再打开，标签和所选清单保持。热角见下一节，没有 Windows 验收。
- **还没有。** 处理模式，以及设置页里除开机启动、热角、搜索条热键、检查更新和「隐藏的应用」以外的项（面板搜索框、面板热键和设置页回收站入口已放弃）。安装版到期通知的点击走 `panel::open_from_notification`，再进 `panel::open_target(PanelTarget::Todo { .. })`。搜索条的待办结果也用这个入口。便携版不注册点击。见「通知」。待办页头部有「悬浮」，打开待办悬浮窗，见「待办悬浮窗」。
- **定位。** `open_target` 先切到待办标签，读最新数据，找到条目后切到它所在的清单、选中并滚动到可见。找不到时停在待办标签并显示「找不到待办」。条目在回收站时切到回收站视图并选中。后者产品规格没有写。
- **当前标记。** 任何状态下都能清除：未完成和已完成的条目在字段区有「设为当前」「清除当前」，回收站里带当前标记的条目在字段区有「清除当前」，行上始终显示「当前」。完成和软删除不自动清除当前标记，规格没有写，服务也不清；清除只通过 `clear_current`。
- **待办页。** 左侧是清单（收件箱按服务给出的顺序，不另外提前）和「回收站」，右侧是新建框、「悬浮」、行列表和选中条目的字段区。「悬浮」打开待办悬浮窗，见「待办悬浮窗」。回收站视图里新建框和「删除清单」不显示，「悬浮」仍在。启动时和每次打开面板都调用 `ensure_inbox`，所以收件箱存在且不重复创建。行上的标记是当前、到期日（逾期时加「逾期」）、周期、来源。来源标记的文字是已保存的 `repo` 和 `number` 拼成的 `仓库#编号`。产品规格没有写标记怎么写，这是当前实现，不是新规则。已完成且不在回收站的行，在勾选旁边显示「取消完成」。点击它或再次点击勾选，都调用取消完成。回收站行显示还剩几天被清除，天数向上取整；30 天的清除由服务在启动时和 `purge_expired` 里做，面板不另建定时器。命令成功后重读服务并推给界面；失败时保留当前状态，在窗口底部显示错误，输入框里的文字不重置。
- **输入。** 输入框用 `TextInput`，因为要读 `preedit-text`：组合输入期间 Enter 不提交。到期日和重复截止日写 `YYYY-MM-DD`（分隔符可以是 `-`、`/`、`.`，月日可以只写一位），提醒写 `HH:MM`，留空是清除。字段只在 Enter 时提交。
- **窗口。** 逻辑尺寸最大 760×560，工作区放不下时每边留 24px 后收小。位置在光标所在显示器的工作区居中。标题栏空白处按下后调用 winit 的 `drag_window`。窗口显示之后拿到过焦点，并且距显示已过 400ms，才把 `Focused(false)` 当成失焦收起，避免从托盘菜单打开时被菜单关闭带来的、迟到的焦点变化立刻收起。每次 `open_target` 或显示都重新计时。这段时间内真的失焦时面板不会自己收起，用户再点外面、按 Esc 或点关闭即可。上面这些数值和位置是实现选择，产品规格没有写。
- **前台。** 热角、托盘「打开面板」「设置」「新建便签」、搜索结果定位都经过 `present`。搜索条热键经过搜索条的 `show`。便签悬浮窗和收纳悬浮窗再次聚焦也调用同一个 `bar_win::bring_to_front`。这些入口不都是用户刚在操作 Lanwork。单独的 `SetForegroundWindow` 会被前台锁拒绝：调用进程不是前台，也不是最近一次输入的接收者。窗口可以已经 `IsWindowVisible`，但落在别的窗口后面。面板把 `visible` 设为真之后，失焦收起还要求这次显示曾经拿到焦点；焦点没到，`Focused(false)` 不会收起，下一次 `show` 仍从已显示走，前台锁继续拒绝。`bring_to_front` 在窗口已经可见时不再 `ShowWindow`，避免多一次失败的激活把失焦消息排进来。最小化时 `SW_RESTORE`，还不可见时 `SW_SHOW`，然后 `BringWindowToTop`、`SetForegroundWindow`，再用 `GetForegroundWindow` 核对（前台若是子窗口，用 `GetAncestor(GA_ROOT)` 认到这个根窗口）。已经是前台就不再注入。还不是时，本进程 `SendInput` 一次相对位移为 0 的鼠标移动（`MOUSEEVENTF_MOVE | MOUSEEVENTF_MOVE_NOCOALESCE`，dx 和 dy 都是 0），等原始输入线程取走后再 `SetForegroundWindow`。`SendInput` 返回只表示事件进了输入流；前台锁看的是已经处理过的最后一次输入，立刻置前会和输入线程竞争。至少等 15ms。`GetLastInputInfo` 的 `dwTime` 比发送前新（`GetTickCount` 回绕时，差值在 `1..0x8000_0000`）之后再等 15ms，避免把发送前已经排着的用户输入当成自己的。最多等 100ms。等待只用睡眠，不抽消息，因为 `present` 还借着面板状态。不送按键。单独的 Alt 抬起不是文档里的「用户按下 Alt」，也会以 `WM_SYSKEYUP` 进到当前前台程序，热角每次失败都会打到浏览器菜单或正在进行的中文输入。不调用 `AttachThreadInput`：置前会同步把激活消息发给前台线程，输入队列附在一起时可能互相等待。相对位移 0 不会移动光标，也不会被前台程序当成按键；系统仍可能丢掉这次空位移，丢掉就等满再试一次置前。真机上各方案能不能拿到前台，用 `tools/foreground` 的 `lanwork-foreground` 看，用法在 `tools/README.md`。那份程序还会试绝对坐标，以及需要显式打开的 Alt 抬起和 `AttachThreadInput`；产品路径不用后两种。面板和搜索条若结束后仍不是前台，就 `hide` 并清掉可见状态，记一条警告，下次触发从隐藏状态再来。若注入在真机上无效，热角会变成弹出后立刻收起；这个收起没有产品规格，待定。直接置前成功不记日志。只有注入之后才到前台时，面板记「面板在注入输入后到前台」，搜索条记「搜索条在注入输入后到前台」。没有窗口句柄时同样收起。悬浮窗没到前台不关闭：规格写的是再次悬浮只聚焦，关掉没有依据。最小化时先还原、拿不到前台就收起，都不是产品规则，规格没有写，待定。没有 Windows 验收记录。
- **产品规格没有写的点，这里的做法，都不是产品规则。** 已完成的条目留在清单里，排在未完成之后。字段（标题、到期日、提醒、周期）仍可改，与服务一致，回收站里的条目不可改，服务拒绝；到期日、提醒、重复截止日的输入格式（`YYYY-MM-DD`、`HH:MM`，留空清除）；回收站行的「剩 N 天」（向上取整）；排序用「上移」「下移」，只和相邻的未完成条目互换；新建框空白或只有空白时显示服务的「标题为空」；清单只提供新建和删除（清单非空时服务拒绝），没有改名和排序。

### 设置页

可见行为见产品规格「设置」。这一版做开机启动、热角、搜索条热键、检查更新，以及「隐藏的应用」。其余设置项没有代码，也没有占位。代码在 `crates/app/src/settings_page.rs`（调用与错误显示）、`crates/app/src/keycap.rs`（录入时的按键拦截）和 `crates/app/ui/settingspage.slint`（版式）。不调用窗口 API 的决定在 `lanwork_core::panel::settings_page`（热角选项与顺序、各行显示的值、开机启动与热角的写盘顺序）和 `lanwork_core::shell`（`capture`：按键换成热键并过滤录入期间的键盘消息；`bind`：`suspend_hotkeys`、`restore_hotkeys`、`save_search_hotkey`；`recording`：录入状态和没注册上的提示）。检查更新的决定在 `lanwork_core::update`，见「更新」。

技术验证里「背景」「渲染器」仍没有通过记录，设置页和面板的其他页一样依赖它们，写在通过之前，记录不因此改变。设置页没有文本输入框，不依赖「中文输入法」。

- **三行。** 从上到下是「开机启动」（开关）、「热角」（右上、左上、左下、右下、关闭五选一，右上是默认）、「搜索条热键」（显示当前组合的框）。文字只有名称、选项名、组合键和错误，没有说明。这三行的位置不因下面的更新块和隐藏列表改变。
- **隐藏的应用。** 关于与更新下面是这一节。名单来自 `Dispatch::hidden_apps`。没有时显示「没有隐藏的应用」。每条右侧是「恢复」，调用 `restore_hidden_app` 写入 `user-apps.json`。写盘失败时把内存改回去，列表不变，错误显示在面板底部。恢复成功后搜索条按当前输入再查一次。
- **控件只显示配置里的值。** 开关不自己翻转，点击只发出相反值的请求；热角点哪项只发出那一项的请求。写盘失败或被拒绝时，Rust 用 `config.json` 当前的值重新推给界面，控件回到原状，错误显示在面板底部的错误条，位置与其他标签一致。切到设置标签、面板重新显示时也按配置重读。
- **开机启动。** `ConfigCommands::set_launch_at_startup` 写 `launchAtStartup`，写成功之后调用 `registry::apply_startup` 写或删 `HKCU\...\Run` 的 `Lanwork`，规则见「开机启动」。写盘失败时不碰注册表，开关回到原值并显示错误。写盘成功而注册表失败时，配置保持新值（与启动时的行为一致，下次启动会再同步一次），开关显示新值，错误条显示「开机启动项未更新：<原因>」并写日志。值没变时仍调用一次注册表同步。
- **热角。** `ConfigCommands::set_hot_corner` 写 `hotCorner`，写成功之后立即调用 `hotcorner::apply`。写盘失败时不调用，热角和显示都保持原值。内容没变时不写盘，也不发布变更。
- **搜索条热键。** 点热键框开始录入，框里显示「录入中」；再点一次、按不带修饰键的 Esc、切换标签、面板收起或失焦都放弃录入。按下组合键即录入。能录的键和修饰键要求与保存、解析相同，热键字符串的格式见「热键」。不在表里的键，或没带修饰键的普通键，结果是「热键无效」，原热键不变。录到的组合走 `save_search_hotkey`，也就是 `save_hotkeys`：先注册新的、成功后写 `config.json`、再卸掉旧的。被别的程序占用时是「热键已被占用」，写盘失败时是写盘错误；`config.json` 和当前注册的热键都保持原样。
- **录入期间不触发已注册的热键。** 开始录入时平台线程把当前注册的热键全部卸掉（`suspend_hotkeys`），否则按下已注册的组合会变成 `WM_HOTKEY`，窗口收不到这次按键。录入期间 `WM_HOTKEY` 即使已经在队列里也不处理。
- **录入只有一个出口。** `HotkeyRecording::end(EndReason)`：录到组合、Esc、录到不能用的键，以及再点一次、失焦、面板收起、切标签、关闭、进程退出，都用它结束，同一次录入只结束一次。失焦包括面板刚显示后 400ms 宽限期内的失焦：宽限期只决定要不要收起面板，不决定要不要结束录入。结束时在同一次平台线程调用里先按配置把热键逐条注册回去，再保存录到的组合。注册回去时一条失败不会卸掉别的：能注册的保留，失败的写日志，并留在上面说的「没注册上」状态里，所以下次打开面板时错误条里仍然看得到。注册回去用新的 id。某个角色没注册上时，保存搜索条热键不去碰它，所以它不会拖住搜索条热键的保存。开始录入时平台线程没有应答的话，也走这个出口，因为那次卸载任务可能稍后才执行。
- **按键拦截。** 面板窗口上装一个窗口子类，在 winit 之前看到键盘消息。录入时吞掉 `WM_KEYDOWN`、`WM_SYSKEYDOWN`、`WM_KEYUP`、`WM_SYSKEYUP` 和字符消息，Alt 组合键不会激活窗口菜单，Esc 不会收起面板。结束录入的那个键还没抬起时，它的自动重复、字符消息和抬起也继续吞掉（`KeyGate`），直到抬起，或又出现一次不是重复的按下。修饰键状态用 `GetKeyState` 读，不读 NumLock。按下消息的 lParam 第 24 位是扩展键标志，交给 `capture_step`：扩展位为 0 且虚拟键码是 Insert、End、Down、PageDown、Left、Clear、Right、Home、Up、PageUp 时，记成 `Numpad0`–`Numpad9`；非扩展的 Delete 是小键盘小数点，不在键名表里，结果是「热键无效」。扩展位为 1 的才是独立的导航键。输入法正在处理的按键（`VK_PROCESSKEY`）当作没按。子类装不上时，热键框显示错误「热键录入不可用」，不卸热键。
- **产品规格没有写的点，这里的做法，都不是产品规则，都标为待定。** 没注册上的热键提示的文字（「搜索条热键已被占用」）、它在所有标签的面板打开时都显示、收起不清；三个控件的形态（开关、分段按钮、点击后录入的框）、行的顺序和位置、行高和标签列宽度；错误显示在面板底部错误条而不是控件旁边，错误文字（「开机启动项未更新：<原因>」「热键无效」「热键录入不可用」，其余用服务的原文）；录入时框里的状态文字「录入中」和放弃的方式（再点一次、Esc、换标签、失焦）；录到不能用的键就结束录入并报错，而不是继续等；不设「恢复默认」按钮，不提供清空；录入不支持 `Win` 组合键里被系统抢先处理的那些（例如 `Win+L`），系统不会把它们交给应用；单按 `Win` 键仍会打开开始菜单，录入不阻止；写盘失败后控件回到的原值是内存里当前的配置，不是上一次读盘的值；开机启动注册表失败时配置保留新值而不回滚（沿用「开机启动」的做法，规格没有写）。检查更新的按钮、说明区域和托盘小点见「更新」。启动后等 1 秒再查、发行说明最多 8000 个标量值、安装包上限 200 MiB、重定向最多 5 次、小点的颜色和大小、说明用固定高度的换行文本，都是实现选择。安静时段、主题、网页搜索引擎等其余设置项本版没有，也没有占位（面板热键与设置页回收站入口已放弃）。没有 Windows 验收记录。

### 热角

可见行为见产品规格「面板」。判定在 `lanwork_core::shell::hotcorner`，不调用 Win32。轮询在 `crates/app/src/hotcorner.rs`。不依赖 `spikes/hotcorner` 这个 crate；那份程序的结论见 [roadmap.md](roadmap.md)「技术验证」。没有对 `lanwork.exe` 的 Windows 验收，也不把 spike 的采样当成性能测量已经达到。

- **轮询。** 线程名 `lanwork-hotcorner`。`hotCorner` 不是 `off` 时，用条件变量超时等待 50ms，醒来读 `GetCursorPos`，并用 `EnumDisplayMonitors` 读每块显示器的 `rcMonitor`。不调用 `timeBeginPeriod`，不安装低级鼠标钩子。光标不在所选角里时不读前台窗口，也不读鼠标按键。在角里时用 `GetAsyncKeyState(VK_LBUTTON)` 读左键，不用本线程的 `GetKeyState`：轮询线程不处理鼠标消息，`GetKeyState` 对不上当前是不是按着。关闭时同一线程停在条件变量上，不再调用 `GetCursorPos`。搜索条热键仍由平台线程 `RegisterHotKey`，关闭热角不卸热键。
- **角。** 每一块显示器的 `rcMonitor` 都参加。区域边长是 `CORNER_EDGE_PX`，当前 32 个物理像素，不按 DPI 放大。规格没有写边长，待定。矩形的右、下是开区间，与 Win32 一致。点同时落在多块重叠矩形的角里时，命中的每一块都算；其中一块被全屏抑制则这一拍不打开。重叠怎么取，规格没有写，待定。点不在任何 `rcMonitor` 内时不在角内。
- **停留。** 从角外进入角内开始用 `Instant` 计时，第一次观察到已经满 350ms 的那一拍打开面板，然后解除武装。停在角内不再打开。这一拍不在任何所选角内时重新武装；角内中途离开再进入，停留从头算。在角内按住左键的拍把已经开始的停留清掉，松开后的第一拍再从头计，见「拖动」。轮询可能让打开晚 0 到 50ms。进程开始，以及从关闭恢复成某个角时，把状态看成在角外：第一拍若已经在角内会开始计时。启动时已经在角内要不要打开，规格没有写，待定。
- **打开。** 到点后在界面线程调用 `panel::show(None)`，与托盘「打开面板」相同。前台和拿不到前台时收起见「面板」的「前台」。界面线程没排上时记一条警告。
- **日志。** 只在状态变化时各记一条，轮询本身不记。角改过来时记「热角：右上」这种名称，关掉记「热角：关闭」。进入角、开始计时记「热角：进入，开始停留」。在角内按住左键、因此不计停留时记「热角：按住左键，不计停留」；按住期间相位不变时不重复记，松开后开始计时仍用「热角：进入，开始停留」。离开并重新武装记「热角：离开，重新武装」；因为关掉而回到空闲时不另记离开。停留到点并且这一拍会打开时记「热角：停留到点，请求打开面板」；到点但被全屏抑制记「热角：停留到点，全屏抑制，不打开」；到点但这一拍的角已经换了、因此不打开，记「热角：停留到点，角已改变，不打开」。面板随后只在注入输入后才到前台时记「面板在注入输入后到前台」；拿不到前台时记「面板没有到前台，已收起」。直接置前成功不另记。这些文字不是产品规则。
- **配置。** 启动时用 `config.json` 的 `hotCorner`。外壳调用 `hotcorner::apply` 立即换角或关闭；设置页写完 `hotCorner` 之后调用它（写盘失败时不调用），见「设置页」。还没启动线程时先记下，启动时用记下的值。换角或关掉时清掉未完成的停留并重新武装。规格没有写切换的瞬间，待定。
- **全屏抑制。** 只看光标命中的那一块显示器上的前台窗口，不枚举别的窗口。抑制条件：前台窗口的类名不是桌面或外壳，并且 `GetWindowRect` 盖住该显示器的整个 `rcMonitor`（左、上小于等于显示器，右、下大于等于显示器）；或者 `SHQueryUserNotificationState` 返回 `QUNS_RUNNING_D3D_FULL_SCREEN`，并且前台窗口与这块显示器相交、矩形为空或读不到。独占全屏的窗口矩形经常不可靠，所以加上后一条。桌面和外壳的类名是 `Progman`、`WorkerW`、`Shell_TrayWnd`、`Shell_SecondaryTrayWnd`、`#32769`，即使盖住显示器也不抑制。不用 `QUNS_BUSY` 和 `QUNS_PRESENTATION_MODE`：前者的官方说明同时包括全屏应用和演示设置，而且不指出是哪一块显示器；后者是演示设置。这两项是否抑制，规格没有写，待定。另一块显示器上的全屏窗口不抑制这一块。规格写的是「有全屏应用时不触发」，没有分开写跨屏，待定。非前台的全屏窗口不看，待定。任务栏自动隐藏时，最大化窗口可能盖住整块 `rcMonitor`，会按同一条几何判定抑制；规格没有写最大化算不算全屏，待定。全屏期间停留到点则解除武装但不打开；全屏结束而光标仍在角内不补开，要先离开再进入。是否应补开，规格没有写，待定。读不到光标或枚举不到显示器时这一拍跳过，不重新武装，也不打开。规格没有写读失败算不算离开，待定。
- **拖动。** 产品规格：按住鼠标左键时不触发，包括把窗口拖过所选角。判定不调用 Win32。轮询在光标已经落在所选角里时读 `GetAsyncKeyState(VK_LBUTTON)`，把高位是否为 1 放进 `Observation::left_button_down`。低位是「自从上次查询以来按下过」，不算按住。`CornerWatch` 看到这一拍为真：不计 350ms，不打开，也不解除武装；已经开始的停留清掉。松开后若仍在角内，从松开后的第一拍重新计时。已经因为停留到点而解除武装的，按住或松开都不重新武装，仍要先离开该角。不调用 `GetGUIThreadInfo`，不看 `GUI_INMOVESIZE`：系统移动循环里左键本身是按着的，自定义拖动也是。右键、中键，左右键对调（`SM_SWAPBUTTON`）时物理右键算不算，以及键盘发起的移动循环（左键没按下）算不算，规格没有写，待定。不因此安装鼠标钩子。
- **空闲。** 关闭时线程阻塞，不再轮询。打开时大约每 50ms 醒一次，只做上面这些查询。没有按「性能测量」对 `lanwork.exe` 采样，不写成已经达到 CPU 或唤醒目标。

### 便签页与悬浮窗

可见行为见产品规格「便签」。代码：`crates/app/src/notes_page.rs`（面板的便签页）、`note_float.rs`（悬浮窗）、`note_editor.rs`（两处共用的保存流程）；版式在 `ui/notespage.slint`、`noteeditor.slint`、`notefloat.slint`，共用控件在 `ui/widgets.slint`。不调用窗口 API 的决定在 `lanwork_core::panel`：`EditSession`（`note_edit.rs`：自动保存的时间、草稿与已保存版本、冲突和失败之后的选择）和 `note_page.rs`（列表与回收站的行、定位、悬浮窗尺寸与错开位置）。保存、冲突、软删除、恢复和永久删除都由 `NoteCommands` 完成，界面不另写规则。「背景」和「渲染器」仍没有通过记录。悬浮窗的来源行和失焦后仍在的亚克力写在下面，不改变那两项的状态。

- **保存。** 正文、标题、标签、置顶有改动后，停止编辑满 1 秒（`AUTOSAVE_IDLE_MS`）自动保存。每次保存带加载时的 `revision`。输入法还在组合（`preedit-text` 非空）时不保存，等下一个周期。标题、标签输入框的 Enter 在组合期间不提交；正文里 Enter 只换行，不提交任何东西。
- **失败。** 自动保存失败时草稿保留在界面里，状态条显示错误和「重试」。要关闭窗口、切换到另一篇、新建或退出时，保存失败就停下，同一条状态条上多出「放弃修改」；重试成功或放弃之后，才继续原来的动作。
- **冲突。** 两处同时改同一篇，后保存的一方得到 `NoteError::Conflict`。窗口保留自己的草稿，显示「保留我的版本」和「保留已保存的版本」。前者在最新 `revision` 上重新保存草稿，后者丢弃草稿并换成磁盘上的版本。选定之前不关闭、不切换。
- **回收站。** 便签页有「回收站」入口，行上显示「剩 N 天」（向上取整），可「恢复」或「永久删除」。删除走 `NoteCommands` 的软删除；30 天的清除由服务在打开时和 `purge_expired` 里做，界面不另建定时器。
- **悬浮窗。** 无边框，使用时创建，关闭时释放。展开时拖动条下面是来源行，再下面是正文，见「来源行」。按便签 id 登记：同一篇已经有悬浮窗时只聚焦它。每篇记住自己的位置和大小：关闭窗口和退出时写进便签文件的 `floatWindow`，重启后再悬浮时放回。写不成时记一条日志，本进程里先用内存里的值。不在叠里的悬浮窗，重启后不会自动重新打开，只是再悬浮时用这个位置。叠起来的在启动时打开当前页，见「叠页」。任务栏不显示。主题变化时重新判断背景，见「背景」。
- **来源行。** 可见行为见产品规格「便签」的「来源行」。不调用窗口 API 的文字在 `lanwork_core::panel::float_source`：`note_source`、`shelf_source`、`todo_source`，间隔号常量 `SOURCE_GAP` 是 `" \u{00B7} "`。过长不在这里截断。界面是 `widgets.slint` 的 `FloatSource`：高 20 逻辑像素，字号 12px，颜色用调色板的 `tertiary`，`overflow: elide`，`clip: true`，文字左边距 12px。三个悬浮窗都把它放在 `x: 0`、`y: 28px`（拖动条下面），宽为整窗，`visible` 在收起时为假。关闭按钮仍在 `y: 0` 的 28×28。拖动条仍是最上 28px，来源行不是拖动目标。便签在打开时、正文编辑时、采用已保存版本时、放弃修改时和保留已保存版本时，用当前草稿重算。面板改了标题或正文，只有 `adopt_if_clean` 成功（没有未保存修改、没有保存问题、输入法不在组合）才换草稿，来源行跟着这份草稿。收纳在打开和 `reload` 时用分组名；分组 `NotFound` 时用 `shelf_source(None)`，显示「收纳」；其它读取错误保留上一行。分组重命名会发布 `EntityChanged`，已经打开的窗口因此重读。待办在打开时设成 `todo_source()`，就是「待办」。叠页的每一页是自己的窗口，藏着的页不显示；看得见的那一页就是自己的来源。翻到某一页时 `present` 按这一页的种类重写来源（便签用当前草稿，待办仍是「待办」，收纳用已经重读的分组名），三种都走这条。页点圆点不画来源行。高、字号和颜色是实现选择，产品规格只要求这一行比正文小、更淡、过长省略。
- **背景。** 可见行为见产品规格「便签」的「背景」。根因：`DWMSBT_TRANSIENTWINDOW` 是桌面背景亚克力。窗口变成非活动（`WM_ACTIVATE` 的 `WA_INACTIVE`）时，桌面窗口管理器按策略把它换成不透明颜色。再设一次 `DWMWA_SYSTEMBACKDROP_TYPE` 取消不了。公开的 `DWMWA_*` 里没有「保持活动时那一层材料」的值。WinUI 把 `DesktopAcrylicController` 的 `SystemBackdropConfiguration.IsInputActive` 留在 true 来保持；那是 Windows App SDK 的合成器，本进程是 Slint 的 HWND，不托管那一层。微软对背景亚克力的说明是：窗口失活时变成纯色。

  展开且 `choose_backdrop` 为亚克力时，`float_backdrop` 返回 `FloatBackdrop::PersistentAcrylic`。`apply_float_backdrop` 先按纯色调用 `apply_dwm`，把系统背景类型设成 `DWMSBT_NONE`，失活策略就没有可关掉的 transient；然后调用未写入公开 `dwmapi.h` 的 `user32!SetWindowCompositionAttribute`，属性 `WCA_ACCENT_POLICY`（19），状态 `ACCENT_ENABLE_ACRYLICBLURBEHIND`（4），`AccentFlags` 为 2。这个标志让强调策略走较新的亚克力配方，但仍走强调策略，不走会在失活时关掉的系统背景。这层在失活时不会被清掉，所以有焦点和没有焦点是同一层。入口找不到或调用失败时退回 `apply_dwm` 的 `DWMSBT_TRANSIENTWINDOW`，那是改之前的行为，失焦仍会变成不透明。纯色时先把强调策略设成关闭，再走原来的纯色回退（`DWMSBT_NONE`，客户区 `#F3F3F3` 或 `#202020`）。收起时同样先关掉强调策略，再走 `apply_collapsed_frame` 的把手：逐像素透明、不圆角、空的模糊区域。着色是 ABGR，浅色 `0x48F3F3F3`、暗色 `0x48202020`：低 24 位与纯色回退相同，高位 `0x48` 是透明度。产品规格没有写这个比例。`frame_policy` 在 `WM_ACTIVATE` 交给 `DefSubclassProc` 之后按当前是展开还是收起重设，失焦后会再写一次这层。便签、收纳、待办三种窗口，以及叠页里重新显示的那一页，都经 `float_frame::sync` 走这一条；`present` 和再次聚焦在 `show` 之后再写一次，因为显示可能把系统背景设回 winit 的默认值 `DWMSBT_AUTO`。页点窗口不是内容窗：`apply_clear_plate` 关掉系统背景和强调策略，再打开空区域的逐像素透明，激活、显示、主题和组合变化时再写一次。搜索条和面板仍直接调用 `apply_dwm`，不走强调策略。拖动过程中这层模糊可能比系统背景亚克力略慢一拍，窗口几何、拖动、关闭和贴边不变。「背景」和「渲染器」的通过记录不因此改变。
- **悬浮窗始终在最上层，贴边收成把手（便签悬浮窗和收纳悬浮窗共用）。** 可见行为见产品规格「便签」「收纳」。待办悬浮窗也走同一套，见「待办悬浮窗」。三个窗口的 `.slint` 都写 `always-on-top: true`，没有钉住按钮。`widgets.slint` 里不再有 `PinBtn`。旧文件里的可选字段 `floatPinned` 仍能读入，反序列化后丢掉，不再写回。贴边写在可选字段 `floatDock`（`edge` 为 `left`、`right` 或 `top`，`offset` 为沿边的物理像素，`collapsed` 表示当前是把手）。`floatWindow` 始终是展开后的矩形，不是把手。`set_float` 同时写这两项，不带 `revision`，不改 `revision`、`updatedAt` 和列表里的置顶；值没变不写盘；回收站里的便签也可以记。不认识的 `edge`（例如 `bottom`）让这一项变成没有贴边，文件其余部分照常打开。字段在文件里，所以随导出、备份、导入整个复制。
  - **几何。** 不调用窗口 API 的部分在 `lanwork_core::panel::float_snap`。屏幕外沿用 `rcMonitor`（不是工作区）。一段边若被另一块屏幕碰到或盖住，那一段从「外侧」里去掉；只露出的一段仍算外侧。底边不产生候选。松手时窗口对应的边离外侧不超过阈值、并且沿边有重叠，才贴上。拖动松手时若还没进这个阈值，先按「工作区」把展开矩形收进 `rcWork`，再用收进去的矩形判断，但只接受松开时越出 `rcWork` 的那一侧，并且这一侧得是可贴的外沿。底边越出时，夹回后上边即使进了阈值也不贴。窗口在越出的方向上铺满工作区时，贴越出的那一侧，不按左、右、上的次序改贴对侧。贴上了就收成把手，滑动仍从松开的位置开始。已经在阈值内的直接贴在 `rcMonitor` 外沿，不先收进工作区。只改大小、再打开和内容撑大不做第二次判断。夹回本身不走系统拖动消息，所以第二次判断写在 `release_float` 里，而不是等下一次 `WM_EXITSIZEMOVE`。同时贴住多段时，先取间隙更小的，一样时先左、再右、再上。点把手或失焦在贴边仍对得上时切换收起；把窗口拖离外侧再松开就取消贴边。位置没动、只改了大小，并且当时是展开的，就保持贴边并按新的大小重新对齐。从把手拖走时，展开尺寸用贴上之前记住的，不用收起后的把手尺寸。沿边位置按把手仍在窗口这段边的正中来回算。收起后的窗口就是把手：厚 `HANDLE_THICKNESS_LOGICAL`（3）逻辑像素、长 `HANDLE_LENGTH_LOGICAL`（40）逻辑像素，按所贴屏幕的 DPI 换成物理像素（96 时厚 3、长 40，144 时厚 5、长 60；横贴时宽高对调）。能点、能悬停的范围就是这块窗口，没有更大的透明点击区。
  - **窗口。** `float_dock.rs` 持有上面的状态。拖动和改大小的结束来自 `WM_EXITSIZEMOVE`（和搜索条共用子类，按窗口句柄分发）。松手后若矩形变了，从松手的位置滑到把手或展开矩形。滑出分成 8 步，每步 20ms。收起或滑动时把最小尺寸放开，否则把手会被 200×120 挡住。展开并且贴边时，窗口内侧靠那条边的正中有同一个把手，再点就收回；它不盖住关闭按钮。收起时客户区背景透明，只画把手：亮色主题 `#5e5e5e`、alpha `0xB8`（约 72%），暗色主题 `#cfcfcf`、同样的 alpha；鼠标停在把手上时更亮、更不透明，亮色 `#b0b0b0`、alpha `0xF2`（约 95%），暗色 `#f4f4f4`、同样的 alpha。两端圆角，半径是厚度的一半。悬停由窗口自己的 `WM_MOUSEMOVE` 调用 `TrackMouseEvent(TME_LEAVE)`，`WM_MOUSELEAVE` 交给界面清掉 `has-hover`。不装全局鼠标钩子。收起时先关掉展开时设过的强调策略亚克力，再由 `apply_collapsed_frame` 关掉系统背景、圆角、边框和非客户区阴影，并再调用一次空区域的 `DwmEnableBlurBehindWindow`。这挡不住一键回到桌面：Win+D 是外壳抬起 `WorkerW`，不一定给这个窗口发 `SC_MINIMIZE`；DWM 的逐像素透明会被清掉，渲染器把客户区清成不透明颜色。重设 DWM 属性盖不住这次清屏。所以收起并且动画已经结束时（这时窗口已经是把手的尺寸），`sync_shape` 用 `SetWindowRgn` 把窗口收成圆角，圆角直径等于客户区较短的一边。`CreateRoundRectRgn` 的右、下是开区间，调用时再少一像素，所以传入的右、下各比把手多 1；不这样加时，40×3 的把手读回来是 (1,0,38,2)，底边和右端被裁掉。区域用窗口坐标：客户区原点可能因为 `DwmExtendFrameIntoClientArea(-1)` 和 `SWP_FRAMECHANGED` 而不在窗口原点上，设区域和读区域都用 `ClientToScreen` 原点减去 `GetWindowRect` 原点。外接矩形用 `GetWindowRgnBox` 对：每一边可以因圆角缩进 1 像素，也可以因 GDI 多出 1 像素，再多就会把把手裁掉。只问有没有区域不够，DWM 重置会留下另一块。区域外的像素不属于窗口，透明被清掉也铺不出方块的角。不另开窗口。收起期间 `WM_SIZE`、`WM_SHOWWINDOW`、`WM_ACTIVATE`、`WM_ACTIVATEAPP`、最小化相关的 `WM_SYSCOMMAND`、带隐藏或最小化坐标的 `WM_WINDOWPOSCHANGING` / `WM_WINDOWPOSCHANGED`、主题、组合、设置、DPI 和显示变化写入 `logs/app.log`。展开后 `SetWindowRgn` 传空。收起和展开的样式在 `WM_SIZE`、`WM_SHOWWINDOW`、`WM_ACTIVATE`、`WM_THEMECHANGED`、`WM_DWMCOMPOSITIONCHANGED`、`WM_SETTINGCHANGE`、`WM_DPICHANGED`、`WM_EXITSIZEMOVE`，以及前台钩子里 `SetWindowPos(HWND_TOPMOST)` 之后，都按当前状态重设；系统若在消息返回后又改回去，子类再投递一条 `WM_APP` 消息补设一次。收起时加上 `WS_EX_TOOLWINDOW`，资源管理器的一键回到桌面不会把它最小化或藏起来；展开后去掉。已经缩成图标，或位置被改到最小化坐标时，收起的窗口用不激活的方式还原后再补设样式。按下就拖动；位移不超过点击阈值时当成点把手，展开。失焦只在展开并且贴边时收回。拖动循环和它结束之后的两轮事件里，迟到的失焦不收回。别的窗口到前台时，对每个悬浮窗再做一次 `SetWindowPos(HWND_TOPMOST, SWP_NOACTIVATE)`；前台如果就是某个悬浮窗，不调整它们之间的先后。这条前台钩子用 `SetWinEventHook(EVENT_SYSTEM_FOREGROUND)`。关闭和退出时写展开矩形和贴边，不写把手的矩形。记下的边对不上当前屏幕时，这一次按 `settle_float` 收进工作区并丢掉贴边，关掉时把丢掉的结果写回去。拖动松手走 `release_float`：先判断贴边，没贴上再 `settle_float`，收进工作区之后再判断一次。改大小松手、再打开和内容撑大只走 `settle_float`，不因此贴边。不贴边时整扇留在工作区里。叠页收起时，看得见的那一页走同一条重设；藏起来的页先卸掉登记再隐藏，避免被这条「收起不许藏」的策略重新显示出来。
  - **这一条没有写进产品规格的做法，都是待定，不是产品规则。** 把手的厚度、长度和颜色已经写进产品规格，上面的颜色值是这个规则的画法。贴上的距离 12 逻辑像素，点击阈值 4 逻辑像素，都按贴住那块屏幕的 DPI 换成物理像素（96 时就是这些数，144 时是 18、6）。同时贴住时的次序是左、右、上。滑动 8 步、每步 20ms。收起的把手可以拖；松手仍在外侧就换位置并保持收起，松手离开就取消贴边并恢复展开尺寸。收起时没有关闭按钮，先展开再关。贴边时从边缘改大小：原点没动只更新尺寸，原点动了按拖动处理。屏幕变了、边不再是外侧时，这一次打开成普通窗口并丢掉贴边，关掉就写成不贴边。贴的是 `rcMonitor`，任务栏挡在边上时把手会盖住那一条任务栏。独占全屏是否盖住 `HWND_TOPMOST` 没有在 Windows 上看过。已经收起时再次悬浮只聚焦，不展开。两块屏幕之间隔 1 物理像素也算外侧，只有边正好接上才挖掉。收起的收纳把手仍是放下目标，能放下的范围就是这块把手。没有 Windows 验收记录。自动测试覆盖外侧判定、贴上、展开收回、拖离、拖出左、右、上边后先收进工作区再收起、DPI 下的把手尺寸，以及 `floatDock` 的读写、旧 `floatPinned` 仍能打开、导出导入。版式测试确认没有钉住按钮、关闭仍在右上、点左边的把手会回调、收起后只画出大约 40×3 的灰把手、鼠标靠近时更亮、暗色主题用更浅的灰。消息策略测试确认收起时在还原、显示、主题、DPI 和再次置顶后要重设样式，并拦住一键回到桌面的隐藏和最小化。Windows 上的探测窗口按把手大小创建（96 DPI 下 40×3）。先前用 48×9 的窗口去等客户区里居中的 (4,3,40×3)，读回来对不上：`SetWindowRgn` / `GetWindowRgnBox` 的坐标相对窗口左上角，客户区原点在扩展框架之后可以不在窗口原点上；探测又把区域抄进 `CreateRectRgn(0,0,0,0)`，`GetWindowRgn` 对这种空目标会返回 `RGN_ERROR`。现在先把圆角和亚克力设回去，再收起，读回的是不圆角、无系统背景。`GetWindowRgnBox` 的外接矩形盖住把手，每一边最多差 1 像素；把手中段和两端内侧的点在区域内。边框色和非客户区策略能设上，这一版 `DwmGetWindowAttribute` 不把这两项读回来。`ShowWindow(SW_MINIMIZE)` 和 `ShowWindow(SW_HIDE)` 之后不留在图标或隐藏状态，区域仍是把手。展开后区域去掉。产品规格写了收起后只看得见把手，一键回到桌面之后也一样。工具窗口和拦住隐藏是当前做法。
- **叠页（便签悬浮窗和收纳悬浮窗共用）。** 可见行为见产品规格「便签」「收纳」。待办悬浮窗加入同一套叠页，页是 `StackPage::Todo`，见「待办悬浮窗」。不调用窗口 API 的规则在 `lanwork_core::panel::float_stack`。窗口协调在 `crates/app/src/float_group.rs`。一叠同一时刻只显示一页的窗口，其余页的窗口藏着、不释放。每一叠展开并且至少两页时，各有自己的彩色圆点行（`ui/stacktab.slint`），挂在内容窗口原来的边框外面、与内容框左边缘对齐，所以 `floatWindow` 仍是内容框，贴边几何不用把页点算进去。页点带 `WS_EX_NOACTIVATE`，`WM_MOUSEACTIVATE` 返回 `MA_NOACTIVATE`，点它不把页点变成前台，贴边展开的那一页因此不会失焦收回。页点句柄登记在同一条前台置顶名单里，前台钩子把它当成自己的窗口，不去把别的悬浮窗再抬一次。内容窗失焦时，若前台是这一叠的页点，或页点正在拖动（含拖动刚结束的两轮），也不收回。少于两页或已经收起时不显示这一叠的页点，收起的把手改画小点。左右键：便签正文的输入框有焦点时交给文字；否则由窗口上的 `FocusScope` 翻页。收纳悬浮窗没有正文输入框，焦点在窗口上时左右键翻页，Enter 仍打开条目。看得见的那一页收起时，和单独一个悬浮窗一样走 `float_frame::sync`：逐像素透明、`WS_EX_TOOLWINDOW`、把手形状的窗口区域，以及显示桌面之后的重设。
  - **成员。** 可选字段 `floatStack`：`id`（同一叠相同）、`index`（页序）、`current`（上次显示的那一页）。便签和分组都可以带。待办悬浮窗的 `floatStack` 记在 `todo-float.json`，不记在清单上，由 `TodoCommands::set_float_stack` 写入，见「待办悬浮窗」。`set_stack` 不带 `revision`，不改 `revision` 和 `updatedAt`；值没变不写盘。缺这一项、`id` 是空白、或形状不是对象，都当成没有叠页，旧文件照常打开。同一个 `id` 凑不齐两页时，打开时清掉这一项。回收站里的便签和已经打不开的收纳不进这一叠，它们的 `floatStack` 清掉。翻页或切到某一页时，目标页没有显示出来就不藏当前还看得见的页，并把打不开的那一页从叠里拿掉。`assemble_stacks` 按 `index` 再按页的种类和 id 排序；同一页出现多次只留排序后的第一次；多个 `current` 留排序后的第一个；一个都没有时当前页是第一页。启动还原用 `plan_startup`：分组和排序相同；正好一个 `current` 时用那一页；缺了或有多个时用记下的 `index` 为 0 的那一页，没有就用排序后的第一页。
  - **松手。** `stack_drop_effect`。没挪够点击阈值就整叠一起动；页点没挪够时换成被按住的那一页（当前做法）。盖住另一个开着的悬浮窗超过一半时：标题栏把整叠并进去，页点只把被按住的那一页并进去。相交面积严格大于较小那个矩形的一半才算，刚好一半不算；同时盖住多个时取相交面积最大的，一样大就留列表里更靠前的。页点离开按下时的矩形（不再超过一半）并且至少两页，就拆出被按住的那一页，不一定是当时显示的页；落回原处不拆。标题栏只移动整叠，离开原处也不拆页。收起的把手拖动不拆页。会贴边时整叠一起贴，不拆页。标题栏不拆页是规格。用较小矩形做分母，以及并进谁，都待定。
  - **合成与拆开。** 合成沿用没被拖动的那一叠的 id、位置和贴边，被拖的页接在后面，已经在里面的不重复，当前页改成被拖的那一叠当时显示的页。拆出一页后还剩至少两页就留在原叠；只剩一页就不再成叠。拆掉的下标在当前页之前，当前下标减一；拆的就是当前页，下标不动并收到最后一页以内；拆的在当前页之后，下标不动。左右翻页到头就停，不循环。叠的 id 形如 `s` 加当前毫秒的十六进制再加序号。这些都待定。
  - **贴边靠近。** 两个都收起、贴在同一块屏幕的同一条边、沿边和垂直于边的间隔都不超过 `DOCK_MERGE_GAP_LOGICAL`（48）逻辑像素（按所在屏幕 DPI 换成物理像素，碰上和重叠算 0）时合成一叠。不同的边不合。上下叠放或左右并排的两块屏幕，即使沿边数字很近，也不是同一条边。把手中心不在任何一块已知屏幕上时不合。这个距离，以及垂直方向也用同一个数，都待定。链式合成最多再跟四次，避免互相触发停不下来。
  - **页点和把手上的点。** 页点是一排彩色圆点，没有页码数字。直径 `DOT_DIAMETER_LOGICAL`（16）、相邻间隔 `DOT_GAP_LOGICAL`（4）、行高 `DOT_ROW_LOGICAL_HEIGHT`（16，与直径相同）逻辑像素。按所在屏幕 DPI 把直径和间隔分别换成物理像素后再相加：宽度是直径乘个数加间隔乘（个数 − 1）。96 DPI 下三页是 56×16，144 DPI 下直径 24、间隔 6、行高 24。左边缘与内容框左边缘对齐，上沿贴着内容框下沿。默认挂在内容框下沿的外面；那样会超出这块显示器的工作区下沿、而上方还有空位时，改挂在框的上方，左边缘仍对齐。水平方向超出工作区时把这一行收进工作区（`fit_dot_row`）。颜色按页序对 8 取余：`#FF5F57`、`#FEBC2E`、`#28C840`、`#5AC8FA`、`#BF5AF2`、`#FF9F0A`、`#FF6B9D`、`#2EB8C8`。当前页不透明，描边 1.5 逻辑像素 `#ffffffb3`，悬停时描边改为 `#ffffff`。其余页透明度 0.42，悬停提到 0.72。超过 `HANDLE_DOT_CAP`（16）只画 16 个，再往后的页没有圆点。把手上页数大于 1 时，仍在 40×3 的灰条里画小点，不画数字，一页一个，当前页更亮；同样超过 16 只画 16 个。一页不画。改挂到上方、圆点的上限都待定。点一下圆点换到那一页。按住圆点拖出才拆页。版式测试用软件渲染确认圆点靠左、按页序红黄绿并在第八页之后回到红、当前页更实且边上有浅色细圈、其余页更透，悬停后其余页更亮，点哪一个圆点回调哪一页。
  - **记住。** 位置、贴边和 `floatStack` 写进每一页自己的文件。关掉叠着的窗口不删成员：窗口释放，页还在文件里；再悬浮某一页时，这一页成为当前页，用记下的位置和贴边打开，其余已打开的页藏起。不在叠里的悬浮窗重启后不自动打开。已经叠起来、并且至少一页记过 `floatWindow` 的，`float_group::install` 排到事件循环的下一轮再调用 `plan_startup`：按 `floatStack.id` 分组，按 `index` 排序，序号有空档也全部留下，只打开当前页的那一个窗口，其余页藏着、不另开窗口。收起时小点画在这一页的把手上；展开时彩色圆点靠左挂在内容框下面。还原成功写一条 `logs/app.log`（`restore_log_line`）。收起窗口的区域消息仍写进同一份日志。藏着的页仍占着窗口，直到进程退出。藏起来之前先 `float_frame::forget`，主题和缩放事件也不再给它重设样式。窗口稍后才就绪时，若这一页已经藏着，同样先卸掉登记再隐藏，不走 `sync`、也不再置前，避免收起的页被「不许藏」重新显示出来。再显示时 `sync` 按当时是收起还是展开重新登记。这些都待定。没有 Windows 验收记录。自动测试覆盖重叠、合成、拆开、翻页到头、标题栏不拆页、页点拖出才拆页、页点行靠左挂在框外、同一块屏幕上把手靠近、不同屏幕的左边不合、打不开的页从叠里拿掉且显示失败时不藏其余页、从文件还原和旧文件没有这一项、启动时把贴在上边并且收起的两格收纳和一篇便签还原成一个窗口、缺了或重复的 `current`、以及 `index` 有空隙。
- **入口。** 便签页「悬浮」按钮；搜索条便签结果 Ctrl+Enter（Enter 打开面板并定位）。`note_float::open_saved` 是快速收集用的：便签已保存时只重试一次悬浮，不创建第二篇，仍失败返回「便签已保存，悬浮失败」。搜索条的收集提交还没有接上，所以这个函数目前没有调用方。
- **变更消息。** 服务发布 `EntityChanged` 后，面板在便签页显示时重读列表，面板编辑区和那一篇的悬浮窗各自调用 `EditSession::adopt_if_clean`：没有未保存的修改、没有保存问题、输入法也没有在组合时，换成最新内容；否则不动，冲突在下一次保存时才出现。记悬浮窗位置不改 `revision`，不会触发这种替换。
- **工作区。** 可见行为见产品规格「便签」的「工作区」。不贴边的展开矩形（含一叠共用的那一份）在拖动松手、改大小松手、按记住的位置打开、以及内容把窗口撑大时，先按与 `rcMonitor` 的重叠面积选屏（含任务栏；只落在任务栏里也算这一块），再整扇收进这一块的 `rcWork`，缩放用这一块的有效 DPI。和任何 `rcMonitor` 都不重叠时，用光标所在显示器。便签、收纳和待办悬浮窗最小 200×120 逻辑像素，按那块屏的有效 DPI 换成物理像素；工作区更小时缩到工作区。不贴边时 `.slint` 的最小宽度是 `min(200px, limit-width)`，最小高度是 `min(120px, limit-height)`，最大宽高是这块工作区的逻辑尺寸，避免工作区更小时最小尺寸把窗口再撑出去。已经记下的宽高仍是物理像素，不按 DPI 重算。贴边对得上时不拉回工作区。页点行用同一块屏的工作区。`contain_float`、`settle_float`、`release_float`、`logical_work_limits`、`fit_dot_row`。拖动松手没贴上时，收进工作区后再判断一次贴边，见「几何」。内容撑大来自窗口的 `Resized`。贴边或滑动中不设工作区上限。`restore_float` 仍是调用方自备物理最小尺寸的旧入口，界面不再调用。待办悬浮窗走同一条路径（`session_for_open`、`absorb_size`、`limit_lengths`），同样限制为最小 200×120 逻辑像素和同样的 `limit-width`、`limit-height`。
- **产品规格没有写的点，这里的做法，都不是产品规则，都标为待定。** 回收站入口放在便签页，规格没有写它在便签页还是设置里。悬浮窗默认 320×360（逻辑像素），位置在光标所在显示器工作区居中，同时打开多个时依次错开 28px，最多 8 步。便签在回收站时拒绝悬浮；便签被删除时已经打开的悬浮窗不关闭、不提示。面板收起不要求先保存，由自动保存继续计时。新建的空便签保留，不因为空而自动删除。标签筛选只支持单个标签，整段相等。按钮和状态条的文字（「新建便签」「置顶」「悬浮」「删除」「恢复」「永久删除」「重试」「放弃修改」「保留我的版本」「保留已保存的版本」「没有便签」）是实现选择。这些文字和数值都没有出现在产品规格里，也没有 Windows 验收记录。

### 收纳页

可见行为见产品规格「收纳」。代码：`crates/app/src/shelves_page.rs`（页面）、`shelf_refs.rs`（页面和悬浮窗共用的条目列表逻辑）、`shelf_float.rs`（悬浮窗）、`shelf_dnd.rs`（OLE 放下目标和拖出）；版式在 `ui/shelvespage.slint`、`ui/shelffloat.slint`。不调用窗口 API 的决定在 `lanwork_core::panel`：`shelf_page.rs`（分组行、保留选中、关联待办的筛选、上移下移、可见条目的路径）和 `shelf_dnd.rs`（放下和拖出的效果判定、拖动阈值、取消）。分组、引用、去重、关联都由 `ShelfCommands` 完成，界面不另写规则。「背景」和「渲染器」仍没有通过记录，本页不改变那两项的状态。

- **布局。** 左侧是分组（名称、条目数；关联了待办的再显示各条待办的标题，多条用「、」连起来，一行放不下就截断）和「新建分组」输入框，右侧是选中分组的名称输入框与动作、条目列表、选中条目的完整路径与动作。没有分组时左侧只显示「没有分组」。待办完成或进入回收站后，分组仍显示该待办标题。选中分组的头部下面列出它关联的各条待办（至多三行可见，其余滚动），每行有「解除关联」，只解除这一条；「关联待办」按钮始终可用，再点就再关联一条。找不到的待办显示「找不到这条待办」，仍可解除。
- **放下。** 放下目标登记在面板窗口句柄上（先 `RevokeDragDrop` winit 登记的，再 `RegisterDragDrop`），只在面板显示、标签是收纳、指针在收纳页区域内、数据里有 `CF_HDROP` 时接受；效果优先复制，其次快捷方式，不返回移动。放下回调先用外壳项（`SHCreateShellItemArrayFromDataObject`，完整路径）读路径，取不到再读 `CF_HDROP`，然后交给后台线程，线程里用 `fs::metadata` 判断是否文件夹，再回到界面线程调用 `add_refs`；目标是放下那一刻选中的分组（页面每次重排时把选中的分组 id 放到一个共享槽里，回调同步读取），没有分组时传空，由服务新建「收纳」；后台探测期间用户换了分组，不改变这次的目标，也不把选中项拉回去。重复路径由服务去重，界面不另提示。路径不是合法 Unicode 时跳过并显示数量。超过 260 个 UTF-16 单元的路径，外壳构造的数据对象在 CI 的 Windows 上给出的是 8.3 短名（指向同一个文件），所以测试只比对文件身份，不比对字符串；存进引用的是外壳给出的那条路径。
- **拖出。** 条目行按下后，指针移动超过 `SM_CXDRAG`/`SM_CYDRAG`（物理像素）才拖出这一条。`DoDragDrop` 是模态循环，不能在面板的借用里跑；推迟到下一轮事件循环又可能已有鼠标抬起入队，循环一开始就看到按钮已松开而结束。所以在拖动阈值触发的那次回调里，借用内只算出要拖的路径并交出，借用一结束就同步进入 `DoDragDrop`；只有这次回调本身落在别的借用里（动作被推迟）时，才退回下一轮事件循环再拖。循环期间面板不因失焦收起。允许的效果只有复制和快捷方式，Esc 取消。结束后补发 `PointerReleased` 和 `PointerExited`。已知路径不存在时不拖出，显示「路径不存在」。
- **路径与图标。** 只对列表里可见的行，在后台线程调用 `check_exists`，并从 `Dispatch::icon_cache` 的共享缓存取图标（搜索条的调度没有打开时用一份独立的壳层缓存）。结果带轮次，换分组或重读时旧轮次的存在结果不覆盖新的。不监视文件系统；切到收纳标签、收纳或待办有变更消息、换分组时才重新检查。网页引用的网站图标不走这份壳层缓存，见「网页引用」。
- **打开。** Enter 或双击用 Windows Shell 打开路径本身（`launch`），Ctrl+Enter 打开路径的上一级目录；已知不存在的路径直接显示「路径不存在」。
- **关联待办。** 「关联待办」弹出搜索框，输入关键字筛选，点击一条即关联；已经关联的那一条再点不写盘。「打开关联收纳」在待办页字段区（回收站里的条目也有），切到收纳并选中关联这条待办的第一个分组。收纳有变更消息时（面板里的收纳页、收纳悬浮窗或服务内部的解除关联引起的都算），面板可见就重排待办页的数据，不论当前停在哪个标签；从别的标签切回待办页时也重排；面板隐藏时不重画，下次显示再读。因此「收纳」标记和「打开关联收纳」不会停在旧状态。
- **悬浮窗。** 分组头部的「悬浮」按钮调用 `shelf_float::open(group_id)`。窗口管理照便签悬浮窗：线程局部的窗口表按分组 id 索引，同一分组已有窗口时只取得焦点；窗口无边框，失焦不关闭；面板自己的失焦收起不变。每个窗口是一个 `ShelfFloat`，只显示该分组的条目，条目列表控件 `RefsList` 与面板共用，选中、打开（Enter、双击、Ctrl+Enter）、拖出、存在性检查、图标都走 `shelf_refs::RefsView`，与面板同一份逻辑。位置和大小存在分组文件的可选字段 `floatWindow`（和便签的 `FloatGeometry` 同一结构），贴边是可选字段 `floatDock`，由 `ShelfCommands::set_float` 一起写入，值没变不写盘；见「悬浮窗始终在最上层，贴边收成把手」。没有这些字段的旧文件照常打开，在第一次记录位置前不会被改写。旧的 `floatPinned` 能读，不再写回。写盘失败时位置只留在内存里并记日志。关闭窗口时记录位置，应用退出时对仍开着的窗口再记录一次；关闭窗口不删除分组。
- **悬浮窗的 OLE 放下。** 每个悬浮窗在自己的窗口句柄上单独登记放下目标（同样先撤销 winit 的登记），状态（`DropState`）和回调里的分组 id 都属于这个窗口，两个窗口互不共享。整个窗口客户区都是放下区（`DropZone::everywhere()`），放下的路径加入该窗口的分组，复用面板的读取路径和后台线程。拖出复用 `shelf_dnd` 的 `DoDragDrop`，只允许复制和快捷方式，Esc 取消。关闭时先停止接受，再释放登记（`Registration` 的 `Drop` 调用 `RevokeDragDrop`），然后隐藏并延后销毁窗口。有测试在两个真实窗口上分别登记、释放其中一个，确认另一个仍然登记着。
- **悬浮窗没有写的点，这里的做法，都不是产品规则，都标为待定。** 悬浮入口按钮的位置（现放在分组头部「删除分组」之前）；默认大小和位置（现用和便签悬浮窗相同的默认尺寸和错位规则）；分组被删除时开着的悬浮窗怎么办（现窗口保留并显示空列表，不自动关闭）；退出重开是否恢复悬浮窗（现不恢复，只记住各分组的位置和大小）。上面这些没有 Windows 验收记录。
- **悬浮窗里移除引用。** 选中一条后，窗口底部出现一行：完整路径和「移除引用」按钮，触发方式沿用面板的按钮。调用 `ShelfCommands::remove_ref`，只删这个分组里的引用，不碰原文件；成功后取消选中并重读。Delete 键、右键菜单、是否确认，产品规格没有写，都待定，现在没有。
- **悬浮窗布局。** 窗口里从上到下是：28px 的拖动条、20px 的来源行（见「来源行」；收起时不占可见内容）、「关联待办」标题行（折叠箭头、文字，有关联时带条数「（N）」）、展开时的关联列表（1 到 4 行，每行 30px，更多时滚动；没有关联时一行「没有关联待办」）、条目列表、选中条目时的底部操作行。Slint 里没有写 `x`、`y` 的子元素会放在父元素正中；展开时父元素变高，没写 `y` 的标题行就被推到列表第一行上，勾选框压在标题文字上。所以这个窗口里每个子元素都写了 `x`、`y`，`ShelfFloat` 还导出各块的屏幕位置，`crates/app/src/float_layout_tests.rs` 用软件渲染的窗口在展开、收起、0 到 9 条关联、有无选中条目的组合下检查它们紧挨着、不重叠、不超出窗口。标题行是否显示条数，产品规格没有写，列入待定。
- **悬浮窗的「关联待办」。** 窗口上沿下面是一个可折叠的标题行「关联待办」，默认收起，展开状态不记住，每次打开悬浮窗都是收起。展开后列出该分组各条关联待办，按关联的先后：一个勾选框、标题。勾选走 `TodoCommands::complete_item`，与待办页同一个逻辑，所以带周期的待办照常生成下一次；已完成、在回收站和找不到的待办，勾选框不可点，也就没有取消完成。点标题调用 `panel::open_target(PanelTarget::Todo)`，打开面板、切到待办并定位该条（找不到时不动）。没有关联时展开显示「没有关联待办」。列表在收纳变更（本分组的关联变了）和待办变更（标题、完成状态变了）时重读；收起时也重读，展开时就是最新的。已完成的标题和回收站里的标题用次要颜色，不另加标记。

### 待办悬浮窗

2026-10-13 决定，同日补了四条：入口是待办页的「悬浮」按钮、已完成的要列出、可以取消完成、逾期是整行文字变红。可见行为以产品规格「待办」的悬浮窗为准。代码在 `crates/app/src/todo_float.rs`、`ui/todofloat.slint`，位置文件在 `crates/core` 的 `todos/float_file.rs`。没有 Windows 验收。「背景」和「渲染器」仍没有通过记录。窗口外观沿用便签悬浮窗，写了也不改变这两项的记录。不新增技术验证项。

已经定下的机制：

- 使用时创建一个窗口，关闭时释放。全程序至多一个。再次打开只聚焦，走和便签悬浮窗相同的 `bring_to_front`。面板失焦不关闭它。退出时记下仍打开的窗口的位置和大小；没有正文要保存。入口是待办页头部的「悬浮」按钮，调用 `todo_float::open`。回收站视图里也有这个按钮，窗口不跟当前清单走。托盘、热键和搜索条是否也能打开，仍待定，现在没有。
- 列表读待办服务里的全部清单，不另存一份，也不按某一个清单 id 或某一个收纳分组过滤。已完成的列出。勾选未完成条目调用 `TodoCommands::complete_item`。取消勾选调用 `TodoCommands::uncomplete_item`，与待办页同一条规则，包括重复待办的下一次。周期生成和下一次的删除仍在待办服务里，悬浮窗不另写一套。失败时窗口上显示错误，行保持操作前的勾选，不写盘。待办的 `EntityChanged` 到达时，窗口开着就按当时的列表规则重读。
- 逾期用已有的 `is_overdue`：未完成、不在回收站、到期日早于今天。整行文字用这个红色。今天的日期与托盘逾期数量同一来源，本地日期来自 `GetLocalTime`。读不到日期时不标红。
- 窗口外观沿用便签悬浮窗：无边框、`always-on-top`、没有钉住按钮、任务栏不显示。展开且透明可用时用失焦后仍在的强调策略亚克力，否则纯色回退，见「便签页与悬浮窗」的「背景」。来源行是「待办」，见「来源行」。图标用 `lanwork-256.png`。贴边和叠页走现有 `float_snap`、`float_dock`、`float_stack`、`float_group`，不另写一套几何。焦点在窗口上时左右键翻页。勾选框是点击区域，不拿键盘焦点。
- 位置记在数据目录的 `todo-float.json`，不写进 `todos/<id>.json`，也不写进 `config.json`。`schemaVersion` 为 1。可选字段与便签相同：`floatWindow`（`x`、`y`、`width`、`height`，物理像素，虚拟屏幕坐标，贴边时仍是展开矩形）、`floatDock`（`edge`、`offset`、`collapsed`）、`floatStack`（`id`、`index`、`current`）。三个字段都可以缺。没有这份文件时，待办照常打开，相当于没记过位置、没贴边、没叠页。缺少 `schemaVersion` 按 1 读取。不认识的 `schemaVersion` 由调用方拒绝这一份窗口记录，文件不隔离、也不写回去，待办清单仍打开。无法解析的 JSON 按「数据」的单文件规则隔离，不碰到清单。不认识的 `edge` 当成没有贴边。写这些字段不改待办的完成状态、`order` 或修订，也不发布 `EntityChanged`。值没变不写盘。写不成时记日志，本进程先用内存里的值。读写这一份文件的命令与 `complete_item`、`uncomplete_item` 分开。
- 这份文件进入导出和备份白名单（`Kind::TodoFloat`），与便签上的悬浮字段一样整份复制。旧包没有这个路径时导入不失败，也不因此拒绝整包。导入按白名单替换：包里没有 `todo-float.json` 时，本地这份文件会被删掉，与其他数据文件相同。已打开的待办服务在同一次 `reload_memory` 里丢掉这份文件的缓存（`known`、`refused`）。随后的读取不把文件写回去；下一次真正记下位置时从磁盘再读，不会把导入前的叠页写回去。`manifest.json` 的 `counts` 不为它加一项，待定；缺这项的旧包仍能导入。
- 叠页里它是 `StackPage::Todo`，没有清单 id，至多一页。启动还原仍用 `plan_startup`：已经叠起来才自动打开。单独一个待办悬浮窗重启后不自动打开。它的 `floatStack` 从 `todo-float.json` 读，和便签、分组的字段一起分组。读这份文件失败或 schema 不受支持时，记日志并跳过这一页，不因此放弃便签和收纳的还原。凑不齐两页时清掉这一项，与现有规则相同。`index` 相同时待办这一页和便签、收纳谁在前，仍是叠页里已经标为待定的页序。当前排序把待办排在便签和收纳之后，不在这里定成产品规则。
- 不贴边时，展开矩形按与 `rcMonitor` 的重叠面积选屏（含任务栏；只落在任务栏里也算这一块），再整扇收进这一块的 `rcWork`，缩放用这一块的有效 DPI。和任何 `rcMonitor` 都不重叠时，用光标所在显示器。打开走 `float_dock::session_for_open` 里的 `settle_float`，不走 `restore_float`。拖动松手、改大小和内容把窗口撑大（`Resized` 交给 `absorb_size`）与便签、收纳同一条路径，不另写一份。拖动过程中调用系统 `drag_window`，不限制离开工作区；拖动松手时若未贴边，才整扇收进所在显示器的工作区（`release_float` / `settle_float`）。
- 窗口默认尺寸 320×360 逻辑像素，最小尺寸 200×120 逻辑像素。不贴边时 `.slint` 的最小宽高同样是 `min(200px, limit-width)`、`min(120px, limit-height)`，最大宽高是这块工作区的逻辑尺寸，避免工作区更小时最小尺寸把窗口再撑出去。

下面这些项已根据实际代码实现敲定：

- 仅从待办页头部的「悬浮」按钮打开，无独立托盘或快捷键。
- 不列出回收站中的条目。不显示清单名，也不分段。行的顺序是清单在服务里的先后；每个清单里未完成在前、已完成在后，各自保持条目在清单里的先后。勾选或取消完成后重读，行按这个顺序重排。
- 仅展示勾选框与标题（`FloatRow` 仅含 `id`、`title`、`completed`、`overdue`），标题以外的标记不显示。点标题没有动作。不能在窗口内排序、软删除、恢复、永久删除、设为当前、处理模式、打开来源、打开关联收纳。
- 逾期条目整行文字标红，使用主题 critical 色值（亮色 `#c42b1c`，暗色 `#ff99a4`）。窗口开着时不建午夜定时器。逾期在待办变更重读、再次打开，或到期提醒调度计算时重算。没有这些事件时，过了午夜也不会自己变红。
- 默认位置在光标所在显示器工作区居中。
- 勾选框不拿键盘焦点，窗口有焦点且至少两页时由左右方向键翻页。
- 贴边与叠页沿用悬浮窗通用机制。

## 通知

到期通知使用操作系统自带的 WinRT `ToastNotificationManager`，由 `windows` crate 调用。不使用 Windows App SDK 的 `AppNotificationManager`：后者要求随包或在机器上部署 Windows App Runtime，解包后的程序还要先调用引导程序。这份运行时不进入本项目。`ToastNotificationManager` 在 Windows 11 上由系统提供。微软目前把该 API 标为维护状态，并推荐 `AppNotificationManager`；若下面的验证失败，先改本节，再决定是否更换 API。

技术验证程序原在 `spikes/toast`（安装版检查通过、便携版点击失败，整体未通过；代码已归档）。这一项仍未通过。便携版点击不定位，不在这里修。主程序还没有 Windows 上的验收记录。托盘徽标不能代替通知通过。

调度在 `lanwork_core::todos` 的 `remind`，不读时钟。外壳在 `crates/app` 的 `remind` 和 `toast`。按下一次要醒的时刻设一个单次定时器，最长 24 小时，到点再算。不按秒轮询。等待已经是 0 时不再立刻重设，避免空转。平台窗口收到 `WM_POWERBROADCAST` 且 `wParam` 为 `PBT_APMRESUMEAUTOMATIC` 或 `PBT_APMRESUMESUSPEND`，以及 `WM_TIMECHANGE` 时，也重新计算。待办或配置变更同样重新计算。

提醒时刻是到期日加上 `HH:MM`，精确到分钟。等于当前这一分钟、且这份键还没发过的，每条各发一条通知，`launch` 是待办 id，点击可以定位。早于当前分钟、还没发过的，收成一次补发。同一分钟的多条不算错过，各发一条。已完成、在回收站、没有到期日或没有提醒的不发。到期日或提醒时刻变了就是另一条。

安静判断是 `in_quiet`。区间是半开的 `[开始, 结束)`。开始等于结束时没有时段。开始大于结束时跨过午夜：分钟大于等于开始，或小于结束。结束那一分钟不再安静。当前分钟落在时段里时不发通知，下一次醒来是时段结束；结束后，压住的提醒按错过合并。`configured_quiet_span` 在 #120 把起止写进设置之前恒为没有时段。调度每次都调用它。不读 `config.json` 的 `quietHours`。设置页不在这一版。

发出去的键记在数据目录的 `reminder-sent.json`，见「数据」。这次发出失败的键只在本进程里压住，不写盘；待办变更、配置变更、睡眠唤醒或时间变化会清掉再试。`Show` 失败时记日志，不崩溃，托盘逾期数量照常重画。读不到本地时间时记日志，不发通知。

通知 XML 是 `ToastGeneric`。一条时 `launch` 是待办 id，正文是标题。多条补发不写 `launch`：规格没有写合并后点哪一条，点这条通知不定位。每条标题各一个 `<text>`，操作中心展开后能看到各条。没有 `<action>`。标题和 id 做 XML 转义，控制字符去掉。显示名来自 AUMID 的 `DisplayName`，正文里不加另一行标题。这几条是当前实现，不是新产品规则。

注册只写当前用户（HKCU），不写 HKLM，也不要求管理员权限。进程调用 `SetCurrentProcessExplicitAppUserModelID`，AUMID 是 `Lanwork`。点击后，`INotificationActivationCallback::Activate` 带回 `launch`。空白则不定位。有 id 时打开面板、切到待办并选中该条。该条已经不在时，面板显示「找不到待办」。注册或 `Show` 失败时不崩溃，只更新托盘逾期徽标。

安装版同时做三件事：

- 在当前用户的开始菜单程序目录放置快捷方式。属性 `System.AppUserModel.ID` 为 AUMID，`System.AppUserModel.ToastActivatorCLSID` 为激活器 CLSID。
- 在 `HKCU\Software\Classes\AppUserModelId\<AUMID>` 写入 `DisplayName` 和 `CustomActivator`（同一个 CLSID）。
- 在 `HKCU\Software\Classes\CLSID\<CLSID>\LocalServer32` 写入本程序路径。进程运行时另外 `CoRegisterClassObject`，让点击落到已经打开的进程；进程已退出时由 `LocalServer32` 再启动。

类工厂和 `INotificationActivationCallback` 放在平台线程的 STA，不实现 `IAgileObject`，也不用自由线程封送。通知平台在另一个进程里 `CoCreateInstance`。自由线程封送的数据包是进程内指针，跨进程解封送失败后，SCM 会再按 `LocalServer32` 启动进程，`Activate` 仍然到不了回调。安装版在这个线程上 `CoInitializeEx(COINIT_APARTMENTTHREADED)`，再 `CoRegisterClassObject`，标志是 `REGCLS_MULTIPLEUSE | REGCLS_SUSPENDED`。界面循环起来之后向这个窗口投递消息，再 `CoResumeClassObjects`。不等待这次调用，避免和 `Activate` 互相等。进程不写注册表，也不另解析 `-Embedding`：安装程序已经写了 `LocalServer32`，进程没在跑时由 SCM 启动 `lanwork.exe`，同一条注册路径接着跑。`Activate` 把 id 交给界面线程，调用 `panel::open_from_notification`。

COM 拉起的本地服务器，启动信息里经常带 `SW_HIDE`。第一次 `ShowWindow` 会改用这个值。这条打开再调用一次 `ShowWindow(SW_SHOWNORMAL)`，并用 `SetWindowPos(SWP_SHOWWINDOW)`。没拿到前台时不收起面板，否则「找不到待办」和选中行都看不见。其它打开面板的路径仍按原来的规则，没拿到前台就收起。

便携版在启动时写 `HKCU\Software\Classes\AppUserModelId\Lanwork` 的 `DisplayName`。不创建快捷方式，不写 `CustomActivator`，不写 CLSID，不注册类对象。便携版通知只显示提醒，点击不定位。2026-10-09 的记录里，便携版通知能显示；运行中点击没有定位，日志没有 `COM Activate`；退出后点击没有拉起进程。这次没有改那条路径。

卸载要删掉上述快捷方式和 HKCU 键，以及 `HKCU\Software\Microsoft\Windows\CurrentVersion\Run` 的值名 `Lanwork`，由安装程序实现。不删除数据目录。便携版运行不删安装版留下的键。AUMID 是 `Lanwork`，激活 CLSID 是 `{E8E9EF84-55BA-4A0C-B4DC-9F9F4A28068D}`，显示名是 `Lanwork`。快捷方式是当前用户开始菜单程序目录里的 `Lanwork.lnk`。`LocalServer32` 的值是带引号的 `lanwork.exe` 路径，规则与开机启动的 `quoted_executable` 相同。通知这一项仍未通过，主程序也没有 Windows 验收。验证程序自己的注销只清理它写过的 spike 标识，不清理产品用的标识。

每次计算都按 `GetLocalTime` 的本地日期重画托盘逾期数量，并让已经打开的待办悬浮窗重读。逾期仍是未完成、不在回收站、到期日早于今天。数量为 0 时不画徽章。徽章的样子沿用「托盘」里已经写下的实现选择，这次不改。没有提醒、也没有时间变化或待办变更时，过了午夜不会自己重画。

## 数据

默认目录：`%USERPROFILE%\Documents\Lanwork`。该目录与 `%USERPROFILE%\Documents\MayDolist` 互不读取。存储层拒绝把数据目录或写入路径解析到 MayDolist 及其子目录，也不创建那个目录。

数据目录按下面的顺序解析，命中即停止：

1. 环境变量 `LANWORK_DATA_DIR`（去掉首尾空白后非空）。相对路径按当前工作目录补成绝对路径。
2. 引导文件 `%LOCALAPPDATA%\Lanwork\bootstrap.json` 的 `dataDir`。引导文件在数据目录之外，迁移之后仍能找到。
3. 默认 `%USERPROFILE%\Documents\Lanwork`。

引导文件是 JSON，字段为 `schemaVersion`（当前为 1）和 `dataDir`（绝对路径）。缺少 `schemaVersion` 时按 1 读取。无法解析、`dataDir` 为空，或 `schemaVersion` 高于当前版本时，解析报错，不改回默认目录。设置里的迁移在校验新目录之后调用存储层写入该文件。写入之前若进程中断，下次启动仍用旧位置。缓存目录固定为 `%LOCALAPPDATA%\Lanwork\cache`，不随数据目录改变。

模块在 `crates/core` 的 `storage`。不依赖 Slint，也不调用 Win32 窗口 API。变更消息在本进程内发布；投递到已打开窗口由后续的应用外壳订阅，不在这一层调用窗口 API。

```text
Lanwork/
├── config.json
├── todo-float.json          待办悬浮窗的位置、贴边和叠页
├── reminder-sent.json       已经发出的到期提醒，不进导出和备份
├── user-apps.json           便携应用、别名和隐藏名单
├── backups/
├── logs/app.log
├── notes/<id>.json          一篇便签一个文件
├── todos/<id>.json          一个清单一个文件，含其中的条目
├── shelves/<id>.json        一个收纳分组一个文件，含其中的引用
└── cache/web-icons/         网站图标缓存，可删除后重建，不进导出和备份
```

数据目录里如果还留着以前的 `github/watchlist.json` 或 `github/cache/`，程序不创建、不读取、不写入这些文件。导入旧包时认出这些路径，不因此失败，也不把它们写进数据目录，也不删除目录里已经有的同名文件。启动时是否清掉这些残留，产品规格没有写，待定。

应用索引和文件图标缓存放在 `%LOCALAPPDATA%\Lanwork\cache`，可删除后重建，不进导出包。网站图标不放这里。它在数据目录的 `cache/web-icons/`，随数据目录走，同样可删除后重建，不进导出和备份。导入按白名单替换时不删除这份目录。

便携应用、别名和隐藏名单在数据目录的 `user-apps.json`。字段见「搜索」。该文件进入导出包，也进入备份。`%LOCALAPPDATA%\Lanwork\cache\apps.json` 可以删除后重建，不能代替 `user-apps.json`。

- 文件名是 id。id 是单个路径分量，不允许分隔符、Windows 保留设备名和文件名非法字符。
- 写入：进程内一把互斥锁。同目录写 `<name>.tmp`，调用 `FlushFileBuffers` 后，目标已存在时用 `ReplaceFileW`（`REPLACEFILE_WRITE_THROUGH`），否则用 `MoveFileExW`（`MOVEFILE_REPLACE_EXISTING | MOVEFILE_WRITE_THROUGH`）。替换失败则删除临时文件、保留原文件，并返回带路径的错误。不自动重试。数据目录位于 OneDrive 同步的「文档」下时，同步进程占用按同一规则报错。
- 单个 JSON 无法解析时，把该文件改名为 `<id>.json.corrupt-<UTC 毫秒>-<序号>` 并记日志，其他文件仍可读。日志不含文件内容。不认识的 `schemaVersion` 不隔离，由调用方拒绝。
- 每个 JSON 对象带数字字段 `schemaVersion`。当前版本是 1。新字段可选并有默认值；缺少 `schemaVersion` 的旧文件按 1 读取。示例模型是 `ExampleDocument`，不是待办或便签模型。
- 写盘成功后发布 `EntityChanged { kind, id, revision }`。`revision` 只在便签保存时携带新的修订号，其他实体为 None。v0.2.0 之后外部 AI 落地时，待办也携带修订号，见 [external-ai.md](external-ai.md)：缺少 `revision` 按 0 读取，不一致则返回「待办保存冲突」；在此之前 `EntityChanged` 保持现在的行为。跨文件批次在提交成功后按写入顺序发布；写盘失败或批次未提交不发布。订阅回调在写锁释放之后执行。
- 日志在 `logs/app.log`。单文件超过 1 MiB 时轮转，保留 `app.log`、`app.log.1`、`app.log.2`。不写文件内容，因此不写便签正文。落盘前去掉常见 GitHub token 形态，以及名称含 `TOKEN`、`SECRET`、`PASSWORD`、`CREDENTIAL`、或以 `_KEY` 结尾且值长度至少 8 的环境变量的值。错误里仍会写出文件路径。
- `import.pending` 的内容是备份绝对路径的 UTF-8 文本，不是 JSON。它不进入导出包。
- 收件箱是 `kind=inbox` 的待办清单，首次需要时创建一次。
- 待办可带到期日、提醒、周期、来源，以及至多一个当前标记。旧记录的来源 `type` 仍是 `github-pr` 或 `github-issue`，并带 `url`、`repo`、`number`，这样已有待办能打开。打开来源只看 URL 是不是 `http` / `https`，不按仓库或编号另做处理。没有再从本机 `gh` 创建来源的服务。每月重复的锚点日是周期上的 `monthDay`（1 至 31）。缺少该字段的旧记录按当前到期日的日子计算。已经写下的 `monthDay` 不因本次到期日落到月末而改掉。
- 取消完成把 `completed` 改回 false，不改 `order`。面板把未完成排在已完成之前，所以该条回到未完成条目里原来的顺序位置。这个先后本身不是产品规则。重复待办在完成并生成下一次时，把那一条的 id 和当时的标题、到期日、提醒、周期、来源写入本条的 `generatedNext`，并把那一条标成 `generatedUntouched`。完成前服务不记录这条关系，下一次只是插在后面的克隆。没有 `generatedNext` 的旧记录取消完成时不猜测要删哪一条。取消完成时，只有该条仍在同一清单里紧跟本条、`generatedUntouched` 仍为真、字段与 `generatedNext` 一致、`everCompleted` 为假、未完成、不在回收站、不是当前、并且没有 `movedAt` 和 `originListId`，才从清单里直接移除。这不是软删除，不写 `todo-purge-pending.json`，也不发 `Purged`。`everCompleted` 在标为完成时写下，取消完成不清，缺字段视为假。改标题、到期日、提醒、周期、来源、排序位置、当前标记、软删除、移动或完成都会清掉 `generatedUntouched`。下一次已被用户改过或已经完成（含完成后又取消完成）时不删除，只把本条标回未完成并清掉 `generatedNext`。这一支产品规格仍待定，不删除是保守处理，不是另一条产品规则。这样移除不通知收纳；下一次若已有关联，规格没有写，这里不解。写盘失败走同一套回滚：内存保持操作前，不发 `EntityChanged`。回收站里的条目服务拒绝取消完成，面板也不显示这个按钮，与回收站不可改一致。
- 收纳服务在 `lanwork_core::shelves`。分组文件是 `shelves/<id>.json`，字段为名称、排序、关联待办 id 的列表 `todoIds`（按关联的先后，没有关联时不写这个字段），路径引用列表 `refs`，以及可选的网页引用列表 `webRefs`。旧文件的单条 `todoId` 读入时成为列表的第一项，之后写这个分组时只写 `todoIds`，不再写 `todoId`。每条路径引用保存绝对路径、显示名、是否文件夹和加入时间，不保存文件内容和图标。每条网页引用保存去掉首尾空白后的网址原文 `url`、去掉首尾空白后的标题 `title`（可以是空字符串）和 `addedAt`。没有图标字段，也不写页面正文。网站图标在数据目录的 `cache/web-icons/`，见「网页引用」。没有 `webRefs` 的旧文件读成空列表。路径规范化和存在性检查见「收纳」。网页引用的比较和挑选见「收纳」的「网页引用」。
- 待办悬浮窗的位置在数据目录的 `todo-float.json`，不写在清单文件里。规格见「待办悬浮窗」。文件在时进入导出和备份白名单。`manifest.json` 的 `counts` 不为它加一项，仍待定。旧包没有这个路径时导入不失败。导入按白名单替换数据文件：包里没有 `todo-float.json` 时，本地这份文件会被删掉，与其他数据文件相同。已打开的服务在这次重载里丢掉这份缓存，随后写位置不会把导入前的叠页写回。
- 已经发出的到期提醒在数据目录的 `reminder-sent.json`。`schemaVersion` 为 1。`sent` 的每一项有 `id`、`due`（`YYYY-MM-DD`）和 `remindAt`（`HH:MM`）。键对不上当前条目的到期日和提醒时刻时，下次记下会去掉，完成或进回收站之后也去掉，这样取消完成且时间没变时不会再发。不进导出和备份。导入按白名单替换时不删除它。不认识的 `schemaVersion` 不隔离、不写回，这次进程只在内存里记。无法解析时按单文件规则隔离，清单仍打开。写失败时内存仍记下，这次进程不反复发；下次启动可能再发一次。写这份文件不发布 `EntityChanged`。
- 便签带递增的 `revision`。保存时带上加载时的 revision，与磁盘不一致则返回冲突错误，调用方保留正文。冲突之后的可见行为以产品规格为准。
- 便签服务在 `lanwork_core::notes`。文件字段还有 `title`、`body`、`tags`、`pinned`、`createdAt`、`updatedAt`、`deletedAt`，以及可选的 `floatWindow`（`x`、`y`、`width`、`height`，物理像素，位置是虚拟屏幕坐标，贴边时仍是展开矩形）、可选的 `floatDock`（`edge`、`offset`、`collapsed`）和可选的 `floatStack`（`id`、`index`、`current`，见「叠页」）。旧文件里的 `floatPinned` 能读，不再写回，与列表里的 `pinned` 无关。旧文件没有 `floatWindow` 或 `floatDock` 照常加载；它们随便签文件进入导出、备份和导入。`set_float` 同时写这两项：不带 `revision`，不改 `revision` 和 `updatedAt`，所以编辑区手里的版本号不会因此过期，列表顺序也不变；回收站里的便签同样可以记。不认识的 `edge` 当成没有贴边。服务不判断记下的值是否还在某个显示器内。时间是 Unix 纪元起的 UTC 毫秒。`deletedAt` 缺省表示未软删除，文件仍留在 `notes/`。标签去掉首尾空白后按原文去重，筛选是去重后的整段相等。列表中置顶在前，其后按 `updatedAt` 从新到旧，再按 id。标题没有非空白字符时显示「无标题」，原文仍写入 `title`。删除写入 `deletedAt`，文件留在 `notes/`。永久删除只删除已经软删除的文件；删文件成功后、发布变更前从内存去掉。进入回收站满 30 天（30×86400000 毫秒）的便签，`deleted` 不再返回，`restore` 不恢复、也不写盘。打开服务时清除一次；外壳也可以调用 `NoteCommands::purge_expired`。服务不建定时器，调用间隔未在规格里写明。某一篇删不掉时记日志并跳过，打开服务仍成功，其余便签照常可用。服务不做覆盖。冲突后的版本选择、关闭和退出时的未保存正文由界面处理。
- 导出包包含配置、待办、便签、收纳分组，以及 `user-apps.json`（便携应用、别名和隐藏名单）。v0.2.0 之后另含已安装插件的副本和启用状态，见 [extensions.md](extensions.md)，现在没有。不含 `github/watchlist.json`、`github/cache`、数据目录里的 `cache/web-icons/`、日志、备份目录、`import.pending`、token 和环境变量。备份同样不含 watchlist、`github/cache` 和网站图标缓存。导入按白名单替换时不删除 `cache/web-icons/`。服务在 `lanwork_core::backup`，薄命令是 `BackupCommands`。包是只含存储法（compression method 0）的 ZIP。根上的 `manifest.json` 有 `packageSchemaVersion`（当前为 1）、`exportedAt`（调用方传入的 UTC 毫秒）、`appVersion` 和 `counts`。新包的 `counts` 不再写 `watchlist` 和 `githubCaches`；旧清单里缺这两项时按 0 读。路径拒绝 `..` 和绝对路径。白名单是上面的数据文件；旧包里的 `github/watchlist.json` 和 `github/cache/<id>.json` 仍能通过校验，导入时忽略、不写入。每个 JSON 可解析；缺少 `schemaVersion` 按 1，高于 1 则整包拒绝。自动备份文件名是 `auto-年-月-日-毫秒.zip`，手动是 `manual-毫秒.zip`，导入前的备份是 `import-毫秒.zip`。`backups/auto-day.txt` 记下最近一次自动备份的公历日，不计入 7 份。同一天再次调用自动备份不再写新文件。自动和手动合计超过 7 份时按文件名里的毫秒删除最旧的，不删除 `import-` 和其他文件。手动备份不改 `auto-day.txt`。调用方传入公历日和毫秒，服务不读时钟，也不读环境变量。
- 不实现 Focus 的聚合服务，也不实现从 MayDolist schema 的一次性迁移。

### 跨文件操作

单文件替换是原子的，跨文件的操作不是。下面三类操作各自保证进程在任意时刻中断后都能恢复到一致状态，不引入通用事务日志。

- **跨清单移动待办**：先写入目标清单（条目带新的 `movedAt` 时间），再从源清单移除。中断后同一 id 出现在两个清单时，加载阶段保留 `movedAt` 较新的一条，并把另一份移除后写回。`movedAt` 相等时保留清单 id 较小的一条；清单也相同则保留靠前的那一行。没有 `movedAt` 的视为更旧。
- **切换当前待办**：先给新条目写上当前标记和 `currentSince` 时间，再清除旧条目的标记。中断后出现多条时，加载阶段保留 `currentSince` 最新的一条，其余清除后写回。`currentSince` 相等时保留清单 id 较小的一条；清单也相同则保留条目 id 较小的一条。没有 `currentSince` 的视为更旧。只有一条当前标记时不改写。

进程仍在、同一批次里后面的写入失败时，先把本批次已经替换的文件写回内存里的操作前内容，然后返回错误。内存保持操作前状态，不发布 `EntityChanged`。这次回滚再失败时，重新读入清单，按上面的 `movedAt` 与 `currentSince` 规则修好后再返回，避免留下重复的条目 id 或两条当前标记。修复成功时返回的仍是原来的写入错误。重新读入失败则返回该读取错误。
- **导入**：由 `BackupCommands` 解压并校验（白名单路径，拒绝 `..` 和绝对路径，每个 JSON 可解析，版本可识别）。校验失败不写 `import.pending`，当前数据不变。通过后，先把当前数据完整备份到 `backups/import-<毫秒>.zip`，再在数据目录写入 `import.pending`（内容是这份备份的路径），然后逐个替换文件、删除导入包中没有的数据文件，最后删除 `import.pending`。旧包里的 `github/watchlist.json` 和 `github/cache` 不写入，也不因此删除数据目录里已经有的同名文件；程序列出的数据文件不含这两处，所以导入不会把它们当成「包里没有」而删掉。替换失败时用这份备份恢复；恢复没有成功则留下 `import.pending`。替换成功后，已打开的配置、待办、便签和收纳从磁盘重新载入，然后才发布 `EntityChanged`。启动时外壳注册的恢复钩子发现 `import.pending`，就用其中记录的备份整体恢复，再删除该文件。`import_recovered` 为真时外壳记日志「导入未完成」，界面尚未显示这句提示。备份文件不存在时不删除 `import.pending`。

加载修复和导入恢复在构建搜索索引、处理通知点击之前完成。`Store::boot` 的顺序是：若存在 `import.pending`，调用导入恢复钩子（备份与导入实现；未注册钩子则启动失败，不加载业务数据）；然后调用加载钩子；然后按注册顺序运行加载修复（`movedAt` 与 `currentSince` 由待办服务实现）。任一钩子返回错误则启动失败，不进入可建索引状态，也不写默认文档。成功之后 `build_index` 与 `handle_notification_click` 才执行调用方。恢复钩子成功且已删除 `import.pending` 时，`BootReport.import_recovered` 为真。外壳记住这个结果并记日志「导入未完成」；界面尚未显示这句提示。导入的 `EntityChanged` 在整次替换完成、已打开的服务重新载入内存之后才发出。永久删除通知是待办服务的领域事件，不是这一层的 `EntityChanged`。永久删除只删除回收站中的条目。从清单删掉之前，把 id 写入数据目录的 `todo-purge-pending.json`（`schemaVersion` 1，字段 `ids`）。这份文件不在 `todos/` 里，避免被当成清单。清单写入成功后发出 `TodoNotice::Purged`。收纳若还没订阅，这条事件不会留下。收纳调用 `watch_todo_notices` 时先订阅，再按这份记录补解除：只解除记录中、且已经不在任何清单里的 id，解除写盘成功后才从记录去掉。记录里的 id 若待办还在，不解除，以免删除尚未落盘时拆掉关联。不在记录里的关联保持原样，读取时也不把残留 id 视为无关联，避免定下「关联到尚不存在的待办 id」。进程在清单写盘之后、收纳写盘之前中断时，下次订阅用同一份记录补上。解除写盘失败时记录还在，下次订阅再试。记录无法读取时不覆盖它，启动加载跳过这一次自动清除，不因此让启动失败。见「收纳」。

待办服务把加载钩子和名为 `movedAt`、`currentSince` 的两条加载修复注册到 `Store::boot`。修复写回使用同一批次，`EntityChanged` 只在该批次提交后发出。永久删除的领域事件是 `TodoNotice::Purged`。服务只删除回收站中的条目。删除前先把 id 写入 `todo-purge-pending.json`，清单写入成功后发出这条事件。启动加载用当时的时间清除已满 30 天的回收站条目；这次清除可能发生在收纳订阅之前，关联靠清除记录补上，不靠重放已经丢掉的事件。

配置至少包括：数据目录、热角、搜索条热键、搜索条位置、安静时段、主题、开机启动、处理模式顺延天数、番茄钟的工作时长、休息时长和长休息时长。不包括玻璃透明度。番茄钟不另存计时记录。旧文件里的 `githubRefreshIntervalMs`、`staleDays`、`sourceSync`、`autoCompleteOnClose` 读取时忽略，不报错，不隔离文件；写回时不再写出。

配置模块是 `lanwork_core::config`。文件是 `config.json`，经存储层读写。字段用 camelCase，`schemaVersion` 当前为 1。缺少 `schemaVersion` 时按 1 读取。无法解析的 JSON 由存储层隔离，外壳改用默认值，不把默认值写回去。JSON 能解析但热键或范围不合法时不隔离、不覆盖，内存里用默认值。不认识的 `schemaVersion` 不隔离，调用方拒绝。

`dataDir` 只是文件里的记录。启动目录仍按环境变量、引导文件、默认目录解析，不读这个字段。`quietHours` 只接受空。非空值返回「安静时段的格式尚未确定」，不写盘。起止格式产品规格没有写，设置页属于 #120。调度里的判断见「通知」，#120 之前不会读这个字段。

`searchBarOrigin` 可选。没有这个字段表示没有记住搜索条位置，显示时用产品规格里的默认位置。有这个字段时是 `x`、`y` 两个整数；缺其中一个，或类型不对，整份配置按字段不合法处理（内存用默认配置，原文件保留）。这两个数的坐标系、屏幕变化和 DPI，产品规格没有写，见「搜索条」的待定项。校验不解释这两个数，负数保留。

下面的缺省不是产品规则，只是文件没写该字段时的值：主题跟随系统，开机启动关闭，`dataDir` 空字符串，安静时段空。产品规格已经写明的默认是：热角右上，搜索条热键 `Ctrl+Alt+M`，没有记住搜索条位置时用光标所在显示器水平居中、上边缘在工作区高度 25% 处，处理模式顺延天数 3（1 至 30），番茄钟 25、5 和 15 分钟。工作时长 1 至 120，休息时长和长休息时长 1 至 60。错误文字是「工作时长只接受 1 至 120 分钟」「休息时长只接受 1 至 60 分钟」「长休息时长只接受 1 至 60 分钟」「处理模式顺延天数只接受 1 至 30」。

## 搜索

应用索引、待办与便签索引、文件索引三者分开。

应用来源：当前用户和公共开始菜单、注册表 App Paths、PATH、商店应用、用户添加的便携应用和别名。按启动目标去重。快捷方式保留参数和工作目录。启动时先加载缓存，再在后台更新。目录变化合并后再重建；注册表、商店应用和手动刷新按来源更新。

应用索引在 `crates/core` 的 `apps`（`lanwork_core::apps`）。枚举用快捷方式、注册表、`shell:AppsFolder`、`ReadDirectoryChangesW` 和 `ShellExecuteExW`，不创建窗口，所以不放进 `crates/app`。便携应用、别名、隐藏和手动刷新的可见入口已写入产品规格。搜索条的应用右键菜单和 Ctrl+Enter 提权已接上。便携应用、别名和手动刷新的界面尚未实现。`AppIndex::refresh` 仍只是进程内重建。目标文件不存在的快捷方式不收录，即使它带 `System.AppUserModel.ID`；同一商店应用仍由 `shell:AppsFolder` 按 AUMID 收录。`shell:AppsFolder` 也列出开始菜单快捷方式带来的桌面应用，它们的解析名是 `Chrome` 这类自定 AUMID 或 `{已知文件夹 GUID}\…\chrome.exe`，不是快捷方式的目标路径，按启动目标去重合不上，同一个应用会出现两条。商店来源因此只收打包应用的 AUMID，形如 `<包名>_<13 位发布者 ID>!<应用 ID>`（`rules::is_package_aumid`）；其余项由开始菜单来源收录，被开始菜单过滤掉的（卸载程序、目标不存在、启动文件夹）也不会从这里回来。商店应用的图标键是 `shell:AppsFolder\<AUMID>`，取图仍走 `SHCreateItemFromParsingName` 和 `IShellItemImageFactory`，得到包里的图标。商店枚举中途失败时该来源整次失败，保留上一次快照。`ShellExecuteExW` 带 `SEE_MASK_NOASYNC`，因为这里没有消息泵，宽字符串在调用返回后释放。

下面是当前实现选择，不是产品规则。PATH 上的 UNC 目录跳过，避免一个断开的网络路径挡住其余来源。开始菜单目录变化的安静时间是 400ms，另有 2 秒上限，到点就重建开始菜单来源。`apps.json` 的 `schemaVersion` 不是 1 时，和无法解析一样隔离成 `apps.json.corrupt-<UTC 毫秒>-<序号>` 并记日志，日志不含文件内容。这和数据目录里不认识的 `schemaVersion` 不隔离不同，因为这份缓存可以重建。读取缓存时的 IO 错误只记日志，不改名。`apps.json` 仍是 schemaVersion 1，新增可选字段 `alternateNames`、`sourcePath`，来源值 `portable` 与 `alias`，以及目标种类 `url`。`sourcePath` 是索引到的文件：快捷方式的 `.lnk`、游戏链接的 `.url`，或直接收录的 exe。旧缓存没有这些字段时按空值读取；没有 `sourcePath` 时，「打开文件所在文件夹」对路径目标退回 exe 自己的目录，「打开目标文件夹」要等下次重建记下快捷方式路径。

开始菜单的 `.lnk` 和收录的 `.url`，显示名用 `SHCreateItemFromParsingName` 得到 `IShellItem`，再 `GetDisplayName(SIGDN_NORMALDISPLAY)`。失败或结果为空白时，用文件名去掉扩展名。快捷方式文件名（含扩展名）和目标 exe 的文件名（含扩展名）作为可搜索备用名，放进匹配引擎的别名字段，不作为结果上的名称。与显示名相同的不重复存。`.url` 没有目标 exe，只加它自己的文件名。

递归扫描开始菜单时，用 `SHGetKnownFolderPath` 取 `FOLDERID_Startup` 和 `FOLDERID_CommonStartup`。目录的规范化路径与其中之一相同则整目录跳过。不按「Startup」或「启动」这些名字判断。测量用的额外目录使用同一组路径，只有扫到这两个已知文件夹才跳过。

卸载程序默认不收录，没有开关。规则对应 Flow Launcher `Plugins/Flow.Launcher.Plugin.Program/Main.cs` 的 `HideUninstallersFilter`，但始终生效。目标文件名（不含目录）忽略大小写等于 `uninst.exe`、`unins000.exe`、`uninst000.exe` 或 `uninstall.exe` 时不收录。目标文件名以该处的前缀开头并且以 `.exe` 结尾时不收录。显示名以前缀开头时不收录。快捷方式文件名以前缀开头并且以 `.lnk` 结尾时不收录。前缀包括 `uninstall`、`卸载`、`卸載`，以及该文件里其他语言的对应词；同一拼写只保留一次。只作用于开始菜单、App Paths 和 PATH。商店应用和用户添加的便携应用不过这道过滤。

收录的 `.url` 只取 `[InternetShortcut]` 段内的第一条非空 `URL=`。地址以 `steam://run/`、`steam://rungameid/` 或 `com.epicgames.launcher://apps/` 开头，且前缀之后还有剩余，才进入索引。比较前缀时忽略 ASCII 大小写。普通 `http` / `https` 以及其他协议不收。去重键是整段地址的 ASCII 小写。启动时把这段地址交给 `ShellExecuteExW`，动词 `open`。不要求本机存在对应的 exe。

`AppSource::ALL` 在四种系统来源之后加上 `Portable` 和 `Alias`。系统来源仍由枚举填入。便携应用和别名来自数据目录的 `user-apps.json`，不由 Windows 枚举产生。便携应用是一条路径目标，来源记为 `Portable`。`kind` 不是路径的便携条目跳过并记日志，不进入索引。别名是一个名称加一个启动目标，来源记为 `Alias`。便携应用与系统来源是同一启动目标时只显示一条，名称用用户填的名称。去重时便携应用不另成一条：系统条目在前时，显示名改成用户填的名称，原来的名称进入备用名；便携应用在前时，后到的系统来源不改显示名。两条系统来源仍保留先出现的名称。别名只并入备用名。别名的目标不在索引里时是否单独显示，待定；最小实现不单独成条。

`user-apps.json` 见「数据」。JSON 的 `schemaVersion` 为 1，字段是 `portable`、`aliases`、`hidden`。缺少 `schemaVersion` 时按 1 读取。文件不存在视为空目录。无法解析，或 `schemaVersion` 更高时返回错误，不改名、不隔离。当前 `load_user_catalog` 和 `save_user_catalog` 仍由调用方传入路径。`AppIndex::open_from_process` 不猜测路径，内存中的目录开始是空的。`set_user_catalog` 替换这份内存并只重建便携应用和别名两个来源。在此之前若后台重建已经用空目录跑完，缓存里残留的便携应用和别名会被清掉。调用方要在打开索引之后把目录设进来。`AppIndex::hide` 和 `restore` 只改这份内存。`Dispatch::hide_app` 和 `restore_hidden_app` 在改完内存后调用 `save_user_catalog` 写入 `user-apps.json`；写盘失败时把内存改回去。隐藏按启动目标的去重键。`entries` 仍包含已隐藏的应用。搜索必须走 `query`，那里丢掉隐藏键。`hidden_apps` 把目录里的隐藏项交给设置页；索引里还能找到同一键时，用当前显示名。

有路径的应用可以「以管理员身份运行」和「以其他用户身份运行」。两者都用 `ShellExecuteExW`，掩码与普通启动相同。动词分别是 `runas` 和 `runasuser`，由系统显示 UAC 提示或凭据对话框。用户取消时 Shell 返回 `HRESULT_FROM_WIN32(ERROR_CANCELLED)`（`0x800704C7`）。这不是失败：不在搜索条显示错误，也不记使用次数。打开目录不在本模块，只返回路径。「打开文件所在文件夹」是索引文件的父目录（`sourcePath`，没有时退回路径目标自己的父目录）。「打开目标文件夹」只在 `sourcePath` 是 `.lnk` 且目标是本地路径时返回目标的父目录。商店应用的目标只有 AUMID，启动串是 `shell:AppsFolder\<AUMID>`。`runas` 不能用来提权打包应用，枚举也拿不到可以交给资源管理器的普通文件路径，包目录通常在受保护的 WindowsApps 下。因此提权和「打开目标文件夹」只对有本地文件的路径目标提供；没有目标时菜单项仍在，但是不可用。快捷键是应用结果上的 Ctrl+Enter 与 Ctrl+Shift+Enter，见产品规格。右键菜单在搜索条里。

待办与便签索引常驻内存，由写盘成功后的变更消息增量更新，查询时不读盘。只收未完成待办的标题，以及不在回收站中的便签的标题、标签和正文。

预计算中文、英文、别名、英文模糊匹配、拼音和首字母。拼音和首字母只用于应用名、待办标题、便签标题和标签；便签正文只做原文子串匹配。拼音表使用固定版本的 Unicode Unihan，读音取 `kMandarin` 与 `kHanyuPinyin` 的并集，去掉声调后去重，并带许可说明。`kMandarin` 只有常用读音，单独使用会漏掉多音字。不做双拼，不按词义猜测读音。查询使用共享索引。

匹配引擎已接在 `crates/core` 的 `search`。打分和索引机制如下。组内排序和最多 20 条的分组配额已写入 [product.md](product.md)「搜索」（规格缺口 #9 第 7 项已定）。从搜索结果打开时次数加 1，也已写入该节。引擎不保存次数。

### 匹配引擎

应用名、待办标题、便签标题、便签标签和别名用同一种 `PreparedCandidate`。调用方把应用名、待办标题和便签标题标成 `FieldRole::Name`，别名标成 `Alias`，标签标成 `Tag`，便签正文标成 `Body`。文件名不走这张拼音表。应用索引查询应用名时已经调用 `MatchIndex`（内部是 `prepare` 和 `query`）。文件索引在 `lanwork_core::files`，不调用 `prepare`。查询调度在 `lanwork_core::dispatch`，对应用、待办和便签调用同一个 `prepare` 和 `query_prepared`。

拼音表在构建 `lanwork-core` 时生成，查询时不下载、不解析 Unihan 原文，也不把查询里的汉字转成拼音。

- 数据来自 Unicode 18.0.0 的 `Unihan_Readings.txt`，文件内日期 2026-07-31。下载地址是 `https://www.unicode.org/Public/18.0.0/ucd/Unihan.zip`。上游全文 SHA-256 为 `9d39995b5de714e8ce93716ed5d15eaa0792d68e407cdf8a0add2893b8f4150b`。仓库里放的是摘录 `third_party/unihan/kMandarin_kHanyuPinyin.txt`：只留 `kMandarin` 与 `kHanyuPinyin`，且码位在扩展 A 或基本区，数据行原样复制。摘录 SHA-256 为 `a5ad0750009db5a4461efc9c66a87c359b9cf7e6e972a6172ba45c673556fa18`。构建时校验摘录，不一致就失败。重现步骤在 `third_party/unihan/extract.py`。
- 许可是 Unicode License v3，全文在 `third_party/unihan/LICENSE.txt`。
- 覆盖 CJK 扩展 A（U+3400–U+4DBF）和 CJK 统一汉字基本区（U+4E00–U+9FFF）。扩展 B 及以后不收入。这一版覆盖 26,711 个有读音的码位、419 个无声调音节。表里没有的字只参与原文匹配。
- 同一码位先保留 `kMandarin` 的书写顺序，再追加 `kHanyuPinyin` 里去声调后还没有的读音。文件里 `kHanyuPinyin` 行排在前面，生成时不沿用这个行序。两个 `kMandarin` 值都保留。不按词义删除读音，多个读音在能否命中上同等。
- 声调符号去掉。`ü` 和带声调的 `ü` 写成 `v`。`ê` 写成 `e`。不做双拼，也不把查询里的声调字母折成无声调拼音。
- 个别读音在源数据里是两个音节连写、中间没有分隔，例如 U+74F2 的 `túnwǎ`。去声调后仍是一个字符串，不猜测切分。
- 生成表映射进进程的数据是 207,860 字节：音节字节、音节偏移、两段码位索引、读音块。这不是「性能测量」里的 Private Bytes。

每个可拼音字段预计算四样东西：归一化原文、去空白形式、按字存放的音节 id、ASCII 词段。不生成多音字的全组合字符串。

- 归一化：全角 ASCII（U+FF01–U+FF5E）折成半角，全角空格折成普通空格，再做 Unicode 小写。不做其他变音折叠，例如 `café` 不会变成 `cafe`。
- 去空白形式是删掉归一化原文里的全部 Unicode 空白。和原文相同时不另存。
- 连续的 ASCII 字母数字是一个词。有读音的汉字记下全部音节 id。没有读音的汉字，以及假名、谚文和其他非 ASCII 字母，记成间隔；拼音和首字母不能跨过间隔。标点只是分隔。
- 正文不建词段和音节，只留原文。

查询先去掉两端空白。剩下没有非空白字符时返回空列表。`query_prepared` 输出命中类型和分数，不截断到 20 条，也不在各组之间分配名额。排序和名额在 `rank_hits`、`allocate_display`。

| 类型 | 条件 | 分数 |
| --- | --- | --- |
| `Exact` | 归一化原文相等，或去空白后相等 | 去掉首尾空白并归一化之后的查询的 Unicode 标量值个数，内部空白计入 |
| `Prefix` | 查询是上述两种形式之一的前缀 | 同上 |
| `Substring` | 查询是上述两种形式之一的子串 | 同上 |
| `Pinyin` | 从某个词段起，用预存音节把查询对齐完，且至少用到一个汉字。最后一个音节可以只匹配前缀 | 同上 |
| `Initial` | 查询的每个字母对齐连续词段的一个首字母。汉字取其任一读音的首字母，英文词取第一个字母 | 同上 |
| `Fuzzy` | 查询每个字符按顺序在归一化原文里命中一次 | 见下 |

同一字段的原文三类只返回最具体的一种。全拼、首字母和英文模糊只在字段不是正文、且查询去掉空白后只含 ASCII 字母数字时才做。纯英文词的对齐不算全拼。同一字段可以同时返回多种命中。别名和标签用 `FieldRole` 与字段序号区分。

英文模糊的分数只在 `Fuzzy` 内部可比：每个命中字符 +1；与上一命中在原文中相邻再 +2；命中点是词首再 +2。词首指串首，或前一字节不是 ASCII 字母数字。取最高分的对齐。其他类型的分数不和模糊分数比较。

`query_prepared` 的顺序是候选项输入顺序、字段输入顺序，然后按原文、全拼、首字母、模糊枚举。这不是组内排序，上面的分数也不参与组内排序。

`rank_hits` 做组内排序。同一个候选项 id 只留一条，命中类型取完全匹配、前缀、全拼、首字母、子串、模糊里最前的一种。然后按这个类型排序。同一种类型里，调用方经 `FrequencySource` 传入的使用频率高的在前。类型和频率都相同，则保持该候选项在输入里第一次出现的相对顺序。引擎不保存使用次数。次数如何加 1 已写入产品规格。本模块仍不把次数写入磁盘，由调用方传入。已接入的便签服务不保存这个次数。

`allocate_display` 按浏览器、应用、待办、便签、网页、文件、文件夹收已经排好的各组结果。每组先取至多 8 条。20 条还没满时，再按同一顺序把前面组剩下的结果取完，再取后面的组，直到满 20 条或没有更多结果。同一组入选的条目在输出里挨在一起。浏览器组只由调用方在 `open_website` 认为输入像网址时放入一条。`SearchGroup::WebSearch` 没有分组序号，`allocate_display` 不收它。「网页」组是收纳里的网页引用，排在便签之后、文件之前。标题走与待办标题相同的 `prepare` 和 `query`；标题为空时不建名称字段。网址只做原文匹配、不做拼音。打开走 `LaunchTarget::Url`。索引读收纳服务的内存，随收纳的 `EntityChanged` 更新。收纳服务打不开时这一组为空。有代码，未在 Windows 上验收。

网页搜索行由调度在输入非空白时接在分配结果之后，所以不占 20 条名额，最多 21 行；产品规格对名额待定。搜索引擎在 `lanwork_core::search::WebSearchEngine`：`google`（默认）、`bing`、`baidu`，地址分别是 `https://www.google.com/search?q=`、`https://www.bing.com/search?q=`、`https://www.baidu.com/s?wd=`，搜索词去掉首尾空白后按 UTF-8 百分号编码，只保留字母、数字和 `-_.~`。名称是「搜索 Google：」「搜索必应：」「搜索百度：」加原样的搜索词。`config.json` 的字段是 `webSearchEngine`，缺省为 `google`；取值不在这三个里时按字段不合法处理，本次用默认配置。启动时 `Dispatch::set_web_search_engine` 读一次配置，设置页还没做，改配置后要重启才生效。用法键是 `UsageKey::WebSearch`，界面不对它 `record_open`。

`cargo bench -p lanwork-core` 用 5,000 个应用名和 10,000 条待办标题测量准备和查询。这组基准不按「性能测量」采样，不能当作应用结果 P95 已经达到。这组语料的 `MatchIndex::heap_bytes()`（各 `Vec` 和 `String` 的 capacity 之和，不含拼音表，不含分配器额外开销）在 Linux 的 debug 构建里是 3,563,603 字节。分配器取整会改变这个数，测试只要求它小于 16 MiB。

### 打开网址

产品规格只要求：输入像网址时，结果最前面有一条名称为「打开网址」的浏览器结果，Enter 或单击用默认浏览器打开；没写协议的补成 `https://`，已经写了 `http` 或 `https` 的按所写协议打开；网页搜索仍在后面。下面怎么判断「像网址」是当前实现选择，不是产品规则。

函数是 `lanwork_core::search::open_website`。搜索条走 `Dispatch::submit`，在 `browser_row` 里调用（原计划的面板搜索框已放弃）。命中时 `SearchGroup::Browser` 放一条，`label` 是「打开网址」，类型文字仍是「浏览器」。`RowDetail::Browser.url` 是要打开的地址。用法键是这个地址，打开后 `record_open`。`location` 留空：将要打开的地址是否画在这一行上，产品规格待定，当前不画。这一条走浏览器组，占最多 20 条里的名额，和原来的浏览器结果一样。网页搜索仍接在 `allocate_display` 之后，名称和搜索词仍用原输入，不改成补全后的地址。

判断步骤：

1. 去掉首尾 Unicode 空白。中间还有空白或控制字符则不是。因此 `cursor .com`、`https://cursor.com/a b` 不是。
2. 含 `@`、`\`、`<`、`>` 或 `"` 则不是。电子邮件不打开。
3. 有 `://` 时，协议只能是 `http` 或 `https`（忽略 ASCII 大小写）。其它协议不是，包括 `file://`、`ftp://` 和 `steam://`。`javascript:` 没有 `://`，后面的主机检查也会失败。写了协议就保留，不把 `http` 改成 `https`。写进地址时协议改成小写，`://` 后面的其余部分原样保留。
4. 没有 `://` 时前面补 `https://`。`http:cursor.com` 这种没有 `://` 的写法不按已写协议处理。
5. 主机必须是下面之一。主机名只接受 ASCII。含非 ASCII 的主机名是否打开，产品规格待定，当前不产生这一条。路径、查询和片段里的非 ASCII 可以保留，例如 `https://cursor.com/文档`。
   - `localhost`，忽略 ASCII 大小写，可以不带点。
   - IPv4：恰好四段十进制，每段 0–255。
   - 方括号里的 IPv6：只含十六进制和冒号，最多一处 `::`。不接受百分号区域标识，也不接受带点的 IPv4 映射写法。不带方括号的 `::1` 不是。
   - 域名：至少一个点。标签用字母、数字和连字符，不能以连字符开头或结尾，每段最长 63，整段主机最长 253。最后一段至少两个 ASCII 字母。因此 `http://x`、`a.b` 不是，`t.co` 是。
6. 端口可选，写在主机后面，十进制 1–65535。`cursor.com:8080`、`https://127.0.0.1:8080/a`、`https://[::1]:443/a` 可以。空端口、0 和超出范围不可以。
7. 端口之后只能是结尾，或路径（`/`）、查询（`?`）、片段（`#`）。这些部分原样保留，不重新编码。`https://cursor.com/dashboard`、`cursor.com/a?q=1#x` 可以。
8. 没有协议、且整个输入只是带一个点的「名称.后缀」时，当前只要后缀是至少两个字母就产生这一条。因此 `readme.md` 也会出现「打开网址」，打开 `https://readme.md`。是否排除这种更像文件名的输入，产品规格待定。

打开和网页搜索是同一条启动路径：`LaunchTarget::Url` 交给 `ShellExecuteExW`，动词 `open`，由系统的默认浏览器处理 `http` / `https`。`crates/core` 不启动浏览器。Alt+数字、悬停选中、单击等同 Enter，都不因为这一条而改变。

文件和文件夹优先使用 Everything，支持 1.4 和 1.5。随包附带 voidtools 的 Everything SDK x64 DLL：1.4 用 SDK 的 DLL，1.5 用 SDK3 的 DLL。两者固定版本，放在程序目录，并附许可说明。每次查询前按 1.5、1.4 的顺序检查状态并探测，不为每次查询启动命令行。

Everything 未运行或未就绪时，退回 Windows Search 索引。查询只匹配文件名，不匹配正文和属性，范围是 Windows 已建立索引的位置。Windows Search 服务不可用时报告文件索引不可用。Everything 恢复就绪后，下一次查询改回 Everything。两种来源都不复制全盘索引。打开文件和文件夹交给 Windows Shell。「打开网址」和网页搜索的地址交给默认浏览器，见「打开网址」。

Windows Search 的 spike 当前做法是进程内 ADO `ADODB.Connection`，提供程序 `Search.CollatorDSO.1`，SQL 含 `System.FileName LIKE`，`TOP` 不超过 50。匹配方式（子串、前缀或整名，以及查询里的 `*`、`?` 和 `LIKE` 的 `%`、`_` 是否同义）待定；产品规格只写到按名称。`ISearchQueryHelper::GenerateSQLFromUserQuery` 的默认语句是 `CONTAINS(*)`，会返回正文命中，不作为产品查询。`ISearchManager` 只用来对照 SQL 和列出索引根。这次做法只说明技术验证里测通的调用，不表示「性能测量」的 P95 已经达到。

文件索引服务在 `lanwork_core::files`，薄命令是 `FileCommands`。搜索条不直接调用它：外壳打开后交给 `Dispatch`，`poll` 在本地结果写出并且距这次输入已满 60ms 时调用 `query`。查询队列、60ms 等待、过期序号和分组合并不在这里；`query` 只把调用方传入的序号原样带回。

每次查询前先检查 Everything，再决定要不要问 Windows Search。状态只有就绪、未就绪、未运行。Windows Search 只有可用、不可用。1.5 的 DLL 能连上但数据库还在加载时是未就绪，不再改问 1.4。1.5 未运行时才探测 1.4。1.5 先连未命名实例，管道不存在再连 `1.5a`。已经连上的客户端在下次查询前只调用 `IsDBLoaded`。探测失败按未运行，日志写服务端版本；读不到时写「未知」，不把 `GetLastError` 的 0 改写成管道不存在。DLL 缺失记一条日志，Everything 按未运行。两个 DLL 都按文件名放在程序目录：`Everything3_x64.dll`、`Everything64.dll`。开发构建在程序目录找不到时，再找仓库 `third_party/everything/`。发布构建不回退到编译机路径。不为查询启动进程，也不复制索引。

Windows Search 沿用上面的 ADO 语句，`TOP 50`。连接字符串能从 `ISearchManager` 读到就用那条，否则用 `Provider=Search.CollatorDSO.1`。服务状态不是正在运行时记为不可用，不打开连接。状态读不到时仍尝试查询。查询失败时同样记为不可用，日志可以带 HRESULT；空的异常 `message` 不作为界面说明。两者都不可用时，结果上的说明只有「文件索引不可用」。查询成功但没有命中是空列表，不是这句说明。`System.ItemType` 等于 `Directory` 标成文件夹，其余标成文件。这是当前实现选择。匹配方式仍待定。

状态检查为就绪但这次查询调用失败时，本次改走 Windows Search，并记日志。规格没有单独写这一步。`Everything3_ConnectW` 在数据库加载时可能长时间不返回，规格没有超时，这里不加。只有 `WSearch` 正在运行才当作可用；正在启动算不算可用，规格没写。

程序目录还要带上两份许可，文件名是 `Everything-SDK3-LICENSE.txt`、`Everything-SDK-LICENSE.txt`，来源是 `third_party/everything/` 里对应的 `LICENSE.txt`。安装程序按清单把它们拷进程序目录，拷贝不在本服务里。清单是 `PROGRAM_DIRECTORY_FILES`。

搜索条的输入先经 `lanwork_core::search::classify_prefix` 判断收集前缀。该函数区分空输入、搜索与收集前缀（便签快速收集 `/note` 仍计划中，待办快速收集已放弃；核心中保留已有的 `parse_todo_due_prefix` 前缀与日期解析代码），并给出前缀之后的剩余文本与是否可提交；不创建记录、不入查询队列。命中前缀时不进入查询队列，尚未返回的查询结果丢弃；未提交的收集文本保存在内存里，退出进程时不保留。

查询队列只保留一个待处理请求，新输入替换旧请求。每次查询有序号，过期序号的结果必须丢弃。应用、待办和便签结果先返回。最后一次输入后 60ms 内没有新输入，才向 Everything 或 Windows Search 发请求并合并结果。每次最多接收 50 条，界面最多显示 20 条。只为可见项取图标。图标缓存同时不超过 128 项和 8 MiB，搜索和收纳共用。

查询调度的代码在 `lanwork_core::dispatch`，类型是 `Dispatch`。搜索条已调用它。`TodoCommands::boot` 成功并且 `NoteCommands::open` 在导入恢复之后完成，才调用 `Dispatch::build`。`Store::build_index` 在启动未完成时不会建索引。索引读的是这两份服务的内存：未完成且不在回收站的待办标题，以及未软删除便签的标题、标签和正文。之后只在 `EntityChanged` 的种类是待办或便签时，从同一份内存重建对应索引。查询不读盘。交给 `Dispatch` 的必须是正在写入的那一份命令；克隆仍是同一份内存。待办在提交批次之前写入内存。便签在写盘或删文件成功之后、发布变更之前更新内存。订阅者读到消息时，这两份内存已是新值。保存或永久删除便签的回调里不要再调用便签写入，写入锁还被这次操作持有。

`submit` 的时钟读数是结果延迟的起点。搜索条先经 `classify_prefix`。空输入和收集前缀不进入查询队列，并使当前序号失效。组合中的预编辑不要调用 `submit`。序号从 1 递增。本地分组写好之后，并且距这次 `submit` 已满 60ms、期间没有更新的输入，才调用文件来源。文件查询返回时序号已经变了就不合并。不可用时结果上的说明是「文件索引不可用」，已有的应用、待办、便签和网页行保留。文件服务最多交回 50 条，显示用 `allocate_display` 收到最多 20 条。

像网址的判断在 `lanwork_core::search::open_website`，见「打开网址」。待办来源校验仍用 `is_http_source_url`，不拿来决定这一条。应用、待办和便签的组内顺序用 `rank_hits`。`record_open` 把对应键的次数加 1，只放在本进程内存里，下一次查询才参与排序。`LatencyRecord::to_json_line` 的字段与 `tools/sample` 的延迟输入一致。终点由调用方用 `mark_rendered` 填上同序号、同一来源的 `end_ns`。被取代的记录单独标出；已经填了终点的记录不再标为被取代。热召回不在这一层。没有按「性能测量」采样时，这些记录不表示目标已经达到。

图标缓存是 `IconCache`。`Dispatch::icon_cache` 把同一份缓存交给收纳。取图只针对当前可见行。Windows 上用 `IShellItemImageFactory::GetImage`，只要图标并缩放到请求边长，再用 `GetDIBits` 读成 RGBA。非 Windows 上取不到图。下面几项规格没有写死，当前做法如下，不把它们当成产品规则：请求边长是 32 像素；快捷方式图标序号只区分缓存键，取图接口没有这个参数；使用次数不落盘；待办、便签和浏览器行没有可交给壳层的路径，不取图标；文件和文件夹保持文件来源的返回顺序，不按次数重排。

## 收纳

服务在 `lanwork_core::shelves`，薄命令是 `ShelfCommands`。一个分组一个 `shelves/<id>.json`。分组保存路径引用和网页引用。服务不调用删除、移动、复制用户文件的接口，也不关闭或移动浏览器标签。界面拖放按本节末尾的原生 OLE 方案。外部拖放的通过条件表见 [roadmap.md](roadmap.md)，七条都已通过，只覆盖文件。收纳页和收纳悬浮窗的代码已写，见「收纳页」，没有 Windows 验收记录。网页引用见本节末尾，排在 v0.2.0 之后，有代码，未在 Windows 上验收。

文件字段：`schemaVersion`、`id`、`name`、`order`、可选的 `todoIds`（旧文件是单条 `todoId`，只读）、可选的 `floatWindow`（悬浮窗的展开位置和大小，缺省表示没记录过）、可选的 `floatDock`（贴边；旧文件的 `floatPinned` 能读，不再写回）、可选的 `floatStack`（叠页，与便签同一结构，见「叠页」）、`refs`。引用字段：`path`、`name`、`folder`、`addedAt`。`addedAt` 是 Unix 纪元起的 UTC 毫秒。不保存文件内容和图标。

### 路径

引用必须是 Windows 绝对路径。相对路径和盘符相对路径（`C:foo`）拒绝。先规范化，再保存和比较：

- 把 `/` 换成 `\`。
- 展开 `\\?\`。`\\?\UNC\`（`UNC` 不区分大小写）改写成 `\\server\share\...`。其他 `\\?\` 只去掉前缀，留下盘符路径。`\\?\Volume{...}` 和 `\\.\` 拒绝。
- 去掉末尾的 `\`。盘符根保留 `C:\` 里的根分隔符，避免变成盘符相对路径 `C:`。UNC 共享根写成 `\\server\share`。
- `.` 和 `..` 按路径段处理，不用字符串前缀裁剪。空段和 `.` 丢掉。`..` 弹出上一段；已经在盘符根或 UNC 共享根上时留在根上。因此 `C:\A\..\AB\x` 与 `C:\AB\x` 相同，`C:\A` 不是 `C:\AB` 的前缀，段名 `foo..` 也不是上级目录。
- 去重键是规范化结果的逐字符简单大写，近似 NTFS 大写表。每个字符取 `char::to_uppercase`，只有结果恰好是一个字符时才替换，否则保留原字符。不按区域设置折叠，也不做随位置变化的 Σ 小写。因此 `İ` 不与 `i` 合并，`ẞ` 不与 `ß` 合并；`σ`、`ς` 与 `Σ` 合并，`ı` 与 `i` 合并。同一分组内键相同则不新增，保留先加入的那条的大小写、显示名、`folder` 和 `addedAt`。不同分组可以各有一条。
- 落盘的 `path` 用规范化形式，分隔符是 `\`，大小写取第一次加入时的写法。
- 显示名取最后一段。没有更短的段时，盘符根用整个 `C:\`，UNC 共享根用共享名。产品规格没有另写显示名，这是存储时的取值。
- `folder` 由调用方传入。`add_refs` 不探测用户路径，避免网络路径在拖入时挂起。

非 Windows 的测试构建还接受以单个 `/` 开头的绝对路径，用 `/` 做同样的段解析，只为在临时目录里断言原文件仍在。Windows 构建不接受这种路径。

### 写入

`add_refs` 的分组 id 为空，且当前没有分组时，新建名为「收纳」的分组，和引用放在同一个文件里一次写入。写盘失败则磁盘上没有这个文件，内存里也没有这个分组，不发布 `EntityChanged`。已有分组但 id 为空时返回错误，不猜测目标。产品规格没有写未选中分组时拖入到哪里。路径列表为空时不新建分组。一批路径里有一条无法规范化，则整批不写。

名称去掉首尾空白，空白则拒绝。分组名称不要求唯一。

删除分组和移除引用只通过存储层改分组数据文件。

一次操作改多个分组文件时，用存储层批次。后面的写入失败，就把本批次已经替换的文件写回操作前内容，不提交、不发布变更，内存保持操作前状态。回滚再失败时重新读入；读入也失败则清空内存，避免继续用和磁盘不一致的分组。

`EntityChanged` 的 `revision` 为 None。回调在存储写锁释放之后执行，此时内存已是新状态。回调里不要再调用本服务的写入。

### 待办关联

一个分组可以关联多条待办，字段是 `todoIds`，按关联的先后。同一条待办在同一分组里只出现一次，再次关联不写盘。一条待办可以被多个分组关联。`unlink_todo(分组, 待办)` 只去掉这一条，其余不动，没有这条关联时不写盘。按待办 id 解除（永久删除时）只从每个分组的列表里去掉这一条，其他关联不动，一次写入各个受影响的分组。

读取旧文件：只有 `todoId` 时，它成为 `todoIds` 的第一项；两个字段都有时合并并去重，`todoId` 在前。读取不改写文件，下一次写这个分组时才只写 `todoIds`。旧版本程序读不到新写的 `todoIds`，这个方向的兼容没有做。导出和导入按整个文件复制，旧的单条字段原样进包，导入后同样读成列表；备份校验只要求 JSON 可解析。

关联只校验待办 id 是不是合法的文件名分量，不检查这条待办是否存在。产品规格没有写关联到不存在的 id 时怎么处理。

服务在 `watch_todo_notices` 里先订阅 `TodoNotice::Purged`，再按 `todo-purge-pending.json` 补解除。只解除记录中已经不在任何清单里的待办 id，写盘成功后从记录去掉。待办还在清单里时不解除。不在记录里的关联不动，因此不会把尚不存在的待办 id 当成已永久删除。订阅前发出的 `Purged` 不会留下；进程在待办写盘之后中断时，下次订阅仍能补上。解除写盘失败时记录还在，下次订阅再试。读取时不把残留 id 视为无关联。

待办完成或进入回收站不改变分组。服务不因这两件事解除关联。

### 存在性

`check_exists` 对每条路径在单独的后台线程里调用 `try_exists`。不打开、不复制、不移动、不删除。每条上限是 2 秒（`EXISTS_TIMEOUT`）。查询没有在上限内返回，包括已断开的 UNC，该条视为不存在。本地路径用同一上限，避免断开的盘符把调用挂住。无法规范化的路径也视为不存在。权限错误和超时都不另报。产品规格要求失效路径显示「路径不存在」，超时按这个结果返回。

界面只对可见条目调用，并在界面线程之外拿结果。不监视文件系统。

### 拖放

外部拖入和拖出用原生 OLE。Slint 1.18.1 的窗口内拖放不能代替它，原因见「运行时」。2026-10-09 的资源管理器手测见 [roadmap.md](roadmap.md)。`24b7624` 上长路径拖入失败；同日 10:56（UTC+8）在 `3311ecc` 上拖入通过。同日 14:10–14:24（UTC+8）条件 7 通过，次数是用户估计。`--slint` 拖放没有路径。通过条件表七条都通过，该项按该表通过，产品用 OLE。下面是早期技术验证里已经观察到的做法。

- 拖入：事件循环线程调用 `OleInitialize`。本机该线程是 `APTTYPE_MAINSTA`（主 STA），不是 MTA。`MainWindow::new` 之前 COM 尚未初始化；进入 winit 事件循环后由 winit 初始化。拿到 HWND 后 `RegisterDragDrop` 返回 `DRAGDROP_E_ALREADYREGISTERED`，于是 `RevokeDragDrop` 再注册自己的 `IDropTarget`。注册之后窗口属性 `OleDropTargetInterface` 的指针与自己的接口相同。验证程序只接受 `CF_HDROP`。产品里的放下目标另外识别「网页引用」里的网址格式。`DragEnter` 只 `QueryGetData`，不 `GetData`。`Drop` 才 `GetData`，先试 `CF_HTML`、`UniformResourceLocatorW`、`text/x-moz-url`、`CF_UNICODETEXT`。读到网址时不再取 `CF_HDROP` 或 `FileContents`。`FileGroupDescriptorW` 里有以 `.url` 结尾的文件名、但解析不出网址时，拒绝这次放下，不把虚拟 `.url` 存成路径。资源管理器拖普通文件时也会带这个格式，文件名不是 `.url` 时仍按路径引用处理。指针在收纳区域外返回 `DROPEFFECT_NONE`；区域内只从源提供的效果里选复制，其次快捷方式，不返回移动。验证程序没有标签，用一个矩形代替收纳区域，区域外的判定有单元测试。产品里仍只在收纳标签显示时接受放下。
- 拖出：按下后，物理像素位移严格超过 `SM_CXDRAG` 或 `SM_CYDRAG` 才调用 `DoDragDrop`。`IDataObject` 用 `IShellItemArray::BindToHandler(BHID_DataObject)`。允许的效果只有 `DROPEFFECT_COPY | DROPEFFECT_LINK`。取消由 `IDropSource::QueryContinueDrag` 返回 `DRAGDROP_S_CANCEL`。`DoDragDrop` 的模态循环会吃掉鼠标抬起，列表行的 `TouchArea` 会一直抓着鼠标，下一次按下仍落在刚才那一行。拖出结束（成功、取消或出错）后要向窗口补 `PointerReleased` 和 `PointerExited`。自动化没有调用 `DoDragDrop`：它要等键盘或鼠标状态变化才会第一次询问是否继续，调用会作用到光标下的窗口。自测用 `dispatch_event` 先拖长路径那一行，再拖文件夹那一行，第二次必须是文件夹。
- 不解析 `.lnk`。合成的 `CF_HDROP` 能读回超过 260 个 UTF-16 单元的路径，`DragQueryFileW` 先问长度再分配。Shell 的 `IDataObject` 对 269 个 UTF-16 单元的路径调用 `GetData(CF_HDROP)` 仍返回 `0x8007007A`：外壳用固定 260 单元组 `CF_HDROP`，这时还没有 `HDROP`。失败后改用 `SHCreateShellItemArrayFromDataObject` 和 `IShellItem::GetDisplayName(SIGDN_FILESYSPATH)`，单元测试读回了原路径，快捷方式路径没有被解析成目标。2026-10-09 10:56（UTC+8）在 `3311ecc` 的 `--ole` 上，资源管理器把这条长路径拖进红色矩形，控制台给出完整 `paths=`，`effect=1`，没有再出现 `0x8007007A`。这次走的是上述外壳项退路。
- 路径是否存在只对可见条目调用上面的 `check_exists`，结果回到界面线程更新。不监视文件系统。
- 不实现物理文件夹同步、文件操作撤销栈和桌面嵌入。

### 网页引用

2026-10-13 决定，排在 v0.2.0 之后。可见行为以产品规格「收纳」的「网页引用」为准。有代码，未在 Windows 上验收。技术验证「网址拖放」已通过，结论见 [roadmap.md](roadmap.md)「技术验证」。通过标准是独立的最小程序取出网址，不包括收纳悬浮窗。

技术验证程序原在 `spikes/urldrop`（已通过验证并归档）。它开一个窗口接受放下，把注册名 `HTML Format`（`CF_HTML`）、`CF_UNICODETEXT`、`UniformResourceLocatorW` 和 `text/x-moz-url` 都写入日志，不从中选一条当作产品规则。`text/uri-list` 若出现也写入日志；2026-10-13 的锁图标和页面链接都没有提供它。标题另记一行：取 `FileGroupDescriptorW` 的文件名，去掉末尾的 `.url`。页面链接的标题是链接文字，与该文件名相同。同一份数据里的 `FileContents` 不调用 `GetData`。产品代码把已经手测过的解析写入 `lanwork_core::shelves::weblink`。

已经定下的机制：

- 与路径引用一样只存引用。不调用会关闭或移动浏览器标签的接口，不把页面正文写入数据目录。
- 面板收纳页和收纳悬浮窗的 OLE 放下目标都识别网址。接受的格式是注册剪贴板格式 `HTML Format`（`CF_HTML`）、纯文本 `CF_UNICODETEXT`、`UniformResourceLocatorW` 和 `text/x-moz-url`。地址栏锁图标和页面链接都走这一条。`DragEnter` 只 `QueryGetData`。`Drop` 才 `GetData`。读到可保存的网址时，不再调用 `CF_HDROP` 或 `FileContents` 的 `GetData`，虚拟 `.url` 不存成路径，也不复制进数据目录。`FileGroupDescriptorW` 里有以 `.url` 结尾的文件名、但解析不出网址时拒绝这次放下。标题取 `FileGroupDescriptorW` 里第一个以 `.url` 结尾的文件名，去掉这个后缀，大小写不敏感。`Cursor Status.url` 的标题是 `Cursor Status`。不用 `CF_HTML` 的文档标题，也不用 `SourceURL`，也不用 `text/x-moz-url` 的第二行。2026-10-13 手测：锁图标没有 `CF_HTML`，页面链接有，文档标题为空；两种拖放都没有 `text/uri-list`。网址在 `CF_UNICODETEXT` 和 `UniformResourceLocatorW`。Chrome 与 Edge 都通过。
- 打开与「打开网址」相同：把保存的网址作为 `LaunchTarget::Url` 交给 `ShellExecuteExW`，动词 `open`，由默认浏览器处理。`crates/core` 不启动浏览器。搜索里的「网页」组走同一条打开，见上面的 `allocate_display`。
- 去重键按产品规格「同一网址只保留一条」：去掉首尾空白，协议和主机名小写，去掉路径末尾的一个 `/`（含问号或井号前的那个）。不改路径其余大小写、`www`、端口、用户名、查询和片段，也不套用路径引用的简单大写。比较范围是全部分组。键相同则不新增，保留先加入的那一条的网址原文、标题和分组。加载时内存里也按这个键只留先加入的一条，写盘要等这个分组下次保存。
- 分组文件另有可选数组 `webRefs`。每项是 `url`、`title`、`addedAt`。`url` 是去掉首尾空白后的原文，不是规范化键。没有这个数组的旧文件读成空列表。路径引用的 `refs` 读法不变。列表里路径引用在前，网页引用在后。分组计数是两者之和。
- 一键浏览器扩展不在拖入这一版，先做 Chrome，其它浏览器更晚。扩展的宿主、安装方式，以及点一下写入的是当前页还是链接，都还没定。扩展落地时同样不得关闭或移动标签。
- 拖入写盘成功之后，以及面板收纳页或收纳悬浮窗把该条列出来且 `cache/web-icons/` 里没有这张图时，在后台线程取图标。用默认浏览器打开该条时，若界面上还没有图标，清掉这次运行记下的失败再取一次。保存和打开都不等这次请求。搜索条里的网页结果仍用类型字形，不读这份缓存。
- 优先页面里 `rel` 为 `icon`、`shortcut icon`、`apple-touch-icon` 或 `apple-touch-icon-precomposed` 的 `<link>`。跳过 SVG。相对地址按最终 URL 解析，按文档顺序尝试，最后试 `{origin}/favicon.ico`。只请求 `http` 和 `https`。带用户信息的地址不请求。
- 失败时图标位留空，不画通用地球图标，条目仍在，不标「路径不存在」。不把失败写进磁盘。同一次进程里，列表触发的失败记在内存，滚动和重读不再请求。打开该条会再试。进程重启后，缓存没有就再取。
- 缓存目录是数据目录下的 `cache/web-icons/`。文件名是规范化键的 SHA-256，扩展名 `.bin`。可以整份删除后重建。读写在 `lanwork_core::web_icons`，不在 `shelves` 里。读到坏文件时只删除这个目录下、文件名是 64 位小写十六进制加 `.bin` 的那一份，不碰到其它路径。不进分组 JSON。导出和备份的白名单不含这个目录。导入按白名单删除包里没有的数据文件时也不删它。分组 JSON 整份进入导出和备份，因此 `webRefs` 跟着走，里面没有图标字节，也没有页面正文。不为图标另加白名单条目。待办悬浮窗的 `todo-float.json` 仍按「待办悬浮窗」进入白名单。

下面是实现选择，不是产品规则。产品规格里对应的项仍待定：

- 格式顺序：先取 `CF_HTML` 里第一个能规范化的 `<a href>`，然后 `UniformResourceLocatorW`，然后 `text/x-moz-url` 的第一行非空行，最后整段去掉首尾空白的 `CF_UNICODETEXT`。一次只保存一条。
- 怎样才算网址：去掉首尾空白后，长度不超过 16384 个字符，中间没有空白，有方案、`://` 和非空主机。方案由 ASCII 字母、数字、`+`、`-`、`.` 组成。不拒绝 `http` / `https` 以外的方案。搜索里「像网址」的判断不拿来当收纳的接受条件。不是一整段网址的纯文本忽略，不显示错误。`CF_TEXT`、ANSI 的 `UniformResourceLocator` 和 `text/uri-list` 仍不读取。
- 同一次拖放里已经读出网址时，只保存这一条网页引用，不另存真实文件。`FileGroupDescriptorW` 里有以 `.url` 结尾的文件名、但四种网址格式都解析不出网址时，这次放下拒绝，不读 `CF_HDROP`。描述符里没有这种文件名、也没有读出网址时，仍按原来的路径引用处理。资源管理器拖普通文件时也会带 `FileGroupDescriptorW`，文件名不是 `.url` 就不当成虚拟网址。只有 `CF_HDROP`、描述符里也没有 `.url` 文件名的真实 `.url` 文件仍是路径引用，不解析文件内容。
- 没有 `.url` 文件名时标题存空字符串。列表和搜索里的名称退回保存的网址。
- 打开：双击、Enter 和现有的「打开」按钮打开保存的网址。单击只选中。Ctrl+Enter 不做任何事，不打开上一级，也不显示错误。搜索里 Enter 或单击打开保存的网址并计一次使用；Ctrl+Enter 和 Ctrl+Shift+Enter 没有动作。
- 网页行不开始拖出。没有网站图标时图标位留空，不标「路径不存在」。后来打不开的网址也不另做「路径不存在」那种提示。

网站图标的获取、失败留空和缓存不进导出已经写在上面。下面这些上限和接口是实现选择：

- HTML 只扫描正文前 512 KiB。单次正文上限 1 MiB。解码后边长不超过 256；原图任一边超过 4096 则不用这张。WIC 先缩小再交给界面。重定向最多 5 次，只跟随 `http` 和 `https`。超时是解析 8 秒、连接 8 秒、发送 10 秒、接收 10 秒。不关闭证书校验，不带 Cookie。页面声明的候选最多 8 条，然后再加 `/favicon.ico`。`data:image` 的 base64 小图直接解码，不另发请求。缓存文件以 `LWFI` 和版本 1 开头，后面是宽、高和 RGBA。读到坏文件就删掉，当作没有缓存。请求前把路径里的 `.` 和 `..` 折起来，路径末尾的 `/` 保留。协议和主机名小写，默认端口不写进地址。
- 挑选地址和可替换的取正文、解码在 `lanwork_core::shelves::favicon`，自己不访问网络。磁盘缓存在 `lanwork_core::web_icons`，只操作数据目录的 `cache/web-icons/`。HTTP 在 `crates/app` 的 `favicon_http`，用已有的 WinHTTP。解码在 `favicon_wic`，用 Windows Imaging Component。PNG 形式的 ICO 目录项色面数和位深是 0。写成 1 和 32 时先改成 0 再解。整份仍解不开、里面嵌着 PNG 时，抽出那段 PNG 再解。`crates/core` 不依赖 Slint，也不调用 Win32 窗口 API。壳层文件图标仍是进程内的 `IconCache`。网站图标不走那份缓存。
- 收纳页和收纳悬浮窗共用进程内的进行中集合和失败集合。列表失败的地址记在失败集合里，滚动和重读不再排进请求。打开该条时从失败集合去掉并记成进行中，然后直接取这一条，不再经过列表的认领；取完从进行中去掉。正在取的不重复排。一张图取到后，两边已经打开的列表都更新。

## 更新

可见行为见产品规格「设置」。版本比较、`latest.json` 和界面状态在 `lanwork_core::update`。WinHTTP、托盘小点和退出后启动安装程序在 `crates/app/src/update.rs` 与 `update_http.rs`。

启动约 1 秒后在后台查一次，进程一直开着时每隔 24 小时再查。设置页「检查更新」马上再查，不等这个间隔。查的是 `https://github.com/wynxing/Lanwork/releases/latest/download/latest.json`。这是最新正式版上的 `latest.json`，不请求 `api.github.com`。GitHub 会先转到同一标签的 `https://github.com/wynxing/Lanwork/releases/download/v<版本>/latest.json`，再转到 `release-assets.githubusercontent.com`。只比较稳定的 `MAJOR.MINOR.PATCH`，`version` 可以带一个 `v`。预发布、多出来的一段和前导零都不算有更新。比较按数字，`0.9` 小于 `0.10`。

有更新时托盘图标右上角加一个小点，设置页显示新版本号；`latest.json` 有 `notes` 时显示发行说明。不自动下载，也不自动安装。已经知道有更新时，后台这次检查失败只写日志，小点和「更新」留着。手动检查失败时设置页显示「检查更新失败」，已经知道的更新仍留着。查到当前版本或没有更新时清掉小点，状态是「已是最新版本」。

安装版点「更新」才下载。便携版没有「更新」，按钮是「打开发布页」，用 `ShellExecuteW` 打开这个 Release 的 `https://github.com/wynxing/Lanwork/releases/...`。安装目录里有 `unins000.exe` 的是安装版。便携版的 zip 里没有这个文件。读不到可执行文件路径时按便携版，不下载安装包。

安装包文件名必须是 `Lanwork-Setup-<版本>.exe`。安装包第一跳必须是 `https://github.com/wynxing/Lanwork/releases/download/v<版本>/Lanwork-Setup-<版本>.exe`。检查更新的第一跳是 `https://github.com/wynxing/Lanwork/releases/latest/download/latest.json`；下一跳只接受同一标签的 `https://github.com/wynxing/Lanwork/releases/download/v<版本>/latest.json`。地址不从 `latest.json` 里读，文件里如果多了网址也忽略。字段是 `version`、`installer.name`、`installer.sha256`（64 位十六进制），可以有 `notes`。已经发布的 v0.3.0 没有 `notes`，程序把它当成没有发行说明，不当成检查失败。文件名不对或哈希不是 64 位十六进制时不静默安装，状态里带「校验信息不可用」，按钮改成「打开发布页」。发布页是 `https://github.com/wynxing/Lanwork/releases/tag/v<版本>`。没有这份文件，或下载下来的字节和 SHA-256 不一致，同样不静默安装。

下载用 WinHTTP，分块写到临时目录，边写边算 SHA-256。不落到数据目录，也不落到缓存目录。不超过 200 MiB。临时文件在校验失败或下载失败时删掉。哈希一致才退出程序。退出仍走原来的便签保存：还有没写盘的修改时不退出，等用户处理完再继续。然后一个 PowerShell 助手等本进程结束（互斥量松开），运行安装包。参数只有 `/VERYSILENT`、`/SUPPRESSMSGBOXES`、`/NORESTART`、`/CLOSEAPPLICATIONS`。没有 `/DIR`，也没有数据目录。安装程序的退出码要检查。不是 0，或者安装程序没有启动时，把退出码写到 `%LOCALAPPDATA%\Lanwork\update-failed.txt`。这个文件不在数据目录里。下次启动读到它就记一条警告，设置页显示「安装失败」，然后删掉文件。自动检查如果仍有新版本，状态保持「安装失败」，「更新」可以再点。用户再点「检查更新」之后按当次结果更新状态。原来的 `lanwork.exe` 还在就再启动它。助手起不来时不退出，设置页显示「安装失败」，临时安装包删掉。

静默安装发现互斥量还在会自己退出，所以必须等进程结束再启动安装包。`/CLOSEAPPLICATIONS` 仍传着。安装脚本 `RestartApplications=no`，避免安装程序再启动一次。

第一跳只允许 https、端口 443，并且没有查询串、片段和 `..`：`https://github.com/wynxing/Lanwork/releases/latest/download/latest.json`，以及钉死的安装包路径和 `latest.json` 版本路径。别的路径不请求。版本路径也可以出现在 `releases/latest/download/latest.json` 的下一跳。`release-assets.githubusercontent.com` 和 `objects.githubusercontent.com` 只允许出现在重定向之后。重定向自己跟，最多 5 次。重定向里的 `..`、百分号编码的 `..` 和其他主机都拒绝。不关闭证书校验。每个请求都带 `User-Agent: Lanwork/<当前版本>` 和 `Accept`。`WinHttpOpen` 的代理名也是这串 `User-Agent`，请求头再用 `ADD` 加 `REPLACE` 写上同一值。元数据不超过 2 MiB。发行说明超过 8000 个 Unicode 标量值时截断并加省略号。这些上限、启动后等的 1 秒、小点的颜色和大小、说明用固定高度的换行文本而不是滚动，都是实现选择。

网络失败时不安装。日志里写失败种类（网络、过大、写入临时文件失败、http 状态码和简要原因）。原因从响应正文抽出，去掉标记和网址，也不写请求地址。正文空着时按状态码写「拒绝访问」「没有这个文件」「请求过多」或「服务器错误」。

不使用 minisign。签名私钥不进仓库，发布脚本也没有可以签名的密钥。同一条发布工作流在安装包生成之后写入 `latest.json` 的 SHA-256。程序只从上面的地址下载并核对。这不是从旧安装目录做完的一次升级。没有那次记录，更新未验收。

便携版不在运行中替换自身。安装程序不安装 WebView2，也不安装 Windows App Runtime。安装版的开始菜单快捷方式和通知激活器按「通知」注册。最低系统版本等产品规格写明之前不判断 Windows build。便携版启动时写 `DisplayName`，不注册点击。安装版的进程侧激活在 `lanwork.exe`，见「通知」。通知这一项仍未通过。

### 安装程序与便携包

安装程序用 Inno Setup 6.7.3。编译器是 `ISCC.exe`。`windows-latest` 可能已经预装别的版本（这次审查时是 6.7.1）。打包脚本不调用那份 `ISCC.exe`。它从 `https://github.com/jrsoftware/issrc/releases/download/is-6_7_3/innosetup-6.7.3.exe` 下载，SHA-256 为 `9c73c3bae7ed48d44112a0f48e66742c00090bdb5bef71d9d3c056c66e97b732`，核对哈希后以 `/PORTABLE=1` 装到 `packaging/.tools/innosetup-6.7.3`，再用那里的 `ISCC.exe`。`ISCC.exe` 的文件版本资源是 `0.0.0.0`，不带参数时的帮助文本也只有 “Inno Setup 6”，都不能区分预装编译器。日志改为用这份 `ISCC` 编译一个空脚本，并打印输出；其中必须有 `Compiler engine version: Inno Setup 6.7.3`。编译器不进 Lanwork 的安装包。

不选 NSIS。它也能在 `windows-latest` 上编出单个 exe，按用户安装也能做，但 `CreateShortcut` 写不了 `VT_CLSID`。不选 WiX。它在 `windows-latest` 上能编，默认产物是 msi；要 exe 还要 Burn。`MsiShortcutProperty` 把快捷方式属性写成字符串，写不成「通知」里用 `InitPropVariantFromCLSID` 验证过的 `VT_CLSID`。

脚本在 `packaging/lanwork.iss`。产物文件名是 `Lanwork-Setup-<版本>.exe`，当前是 `Lanwork-Setup-0.3.1.exe`。`PrivilegesRequired=lowest`，不请求管理员，不写 HKLM，不安装 WebView2，不安装 Windows App Runtime。默认目录是 `%LOCALAPPDATA%\Programs\Lanwork`。这是实现选择，产品规格没有写安装目录。用户可以改目录。目录里有 `"` 时安装停止。Inno Setup 6.7.3 拒绝 `MinVersion=0`，编译器要求至少 `6.1`。脚本写 `MinVersion=6.1`，这是编译器下限，不是产品最低版本。产品最低 build 仍待定，安装程序不判断 Windows 11 的 build。

开始菜单快捷方式在当前用户的程序目录，文件名 `Lanwork.lnk`。Inno 的 `[Icons]` 写不了属性存储。安装结束时从临时目录运行 `lanwork-shortcut.exe`（`tools/shortcut`），写入 `System.AppUserModel.ID` 和 `System.AppUserModel.ToastActivatorCLSID`，然后删掉这个小程序，不留在安装目录。标识见「通知」。`DisplayName`、`CustomActivator` 和带引号的 `LocalServer32` 由安装脚本写入 HKCU。

交互安装时，若互斥量 `Local\Lanwork.SingleInstance.Mutex` 还在，安装程序提示先关掉 Lanwork。静默安装发现这个互斥量还在就退出，不结束进程。文件被占用而互斥量已经不在时，交互安装仍提示关闭；静默安装这时会按 Inno Setup 的默认关掉占用进程。CI 的静默安装只在进程没运行时执行。

卸载删掉安装目录里这次装上的文件、开始菜单快捷方式、上面的 HKCU 键，以及 Run 里的值名 `Lanwork`。不删 Run 这个键本身。不删 `%USERPROFILE%\Documents\Lanwork`。不删 `%LOCALAPPDATA%\Lanwork` 下的引导文件和缓存。安装目录在 `%LOCALAPPDATA%\Programs\Lanwork`，和缓存目录不是同一个。安装不写 Run 值；开机启动仍由程序按配置写。卸载才删这个值。

程序目录里的文件：`lanwork.exe`、`PROGRAM_DIRECTORY_FILES` 的四个文件、`Unicode-LICENSE.txt`（`third_party/unihan/LICENSE.txt`）、`THIRD_PARTY_NOTICES.txt`。图标用 `crates/app/assets/lanwork.ico`。向导用 tag `is-6_7_3` 里非官方的简体中文消息 `Files/Languages/Unofficial/ChineseSimplified.isl`，副本是 `packaging/ChineseSimplified.isl`（20905 字节，LF）。编译器安装程序不拷贝 Unofficial 目录，所以脚本不写 `compiler:Languages\...`。翻译版权是 Copyright (c) 2019 - 2020 kirakira，MIT 许可正文在 `packaging/ChineseSimplified-LICENSE.txt`，上游是 <https://github.com/kira-96/Inno-Setup-Chinese-Simplified-Translation>。Inno Setup 本体的版权是 Copyright (C) 1997-2026 Jordan Russell，部分版权 Copyright (C) 2000-2026 Martijn Laan。许可要求的条件原文在 `packaging/Inno-Setup-License.txt`（同一 tag 的 `license.txt`），条件不改。这两份许可写入安装目录和便携版里的 `THIRD_PARTY_NOTICES.txt`。欢迎页关掉。这些文字是安装器的实现选择，不是产品规格里的界面文案。「背景」和「渲染器」仍没有通过记录，打包不改变那两项。

便携版是 zip，文件名 `Lanwork-<版本>-portable-x64.zip`，当前是 `Lanwork-0.3.1-portable-x64.zip`。内容与安装目录相同，不含安装程序，不含 `lanwork-shortcut.exe`，也不含 `unins000.exe`。程序用这个文件区分安装版和便携版，见「更新」。便携版启动时写 `DisplayName`，不注册点击激活。见「通知」。

版本只有 Cargo workspace 的 `0.3.1`。安装包的 `AppVersion`、`VersionInfoProductVersion` 和 exe 资源里的 `FileVersion`、`ProductVersion` 字符串都是这个值。安装包文件版本资源的四段整数是 `0.3.1.0`。

打包脚本在编完 release 之后、以及静默安装之后，各读一次 `lanwork.exe` 的 PE 可选头。`Subsystem` 必须是 2。这是 `IMAGE_SUBSYSTEM_WINDOWS_GUI`。快捷方式工具 `lanwork-shortcut.exe` 仍是控制台程序，不留在安装目录，不查它的子系统。

推送与 Cargo 版本一致的 `v*` tag 时，`.github/workflows/release.yml` 在 `windows-latest` 上编 release、打安装包和便携版、创建 GitHub Release，并上传这两个文件和 `latest.json`。`latest.json` 由 `packaging/build.ps1` 在安装包生成之后写入，内容是版本、发行说明、`Lanwork-Setup-<版本>.exe` 和该文件的 SHA-256。发行说明用同一份发布说明。已经发出的 v0.3.0 文件没有发行说明。说明里放 Slint 徽标和 <https://slint.dev> 的链接，并说明第三方许可。仓库已经公开，Release 按公开发布。不生成 minisign 签名。程序按「更新」下载并核对。未登录浏览器打开 Release 页、确认徽标和链接的记录还没有。

Pull request 的 CI 用同一套打包脚本试装：静默安装到带空格和中文的目录，再卸载，把安装包和便携版上传为 artifact，不创建 Release。这次静默安装不是 Windows 上的人工验收，也不是升级验收。

## 性能测量

下面的数字是测量协议和目标，还没有一次符合协议的记录。空 Slint 窗口的采样记在 [roadmap.md](roadmap.md)「技术验证」，那次没有加载固定数据，不填进下表。在有一次符合协议的记录之前，文档和界面都不写「已达到」。禁止为了凑数字裁剪工作集。Everything 客户端、Everything 服务、Windows Search 索引服务和安装程序单独记录，不计入 Lanwork 进程。随包的 Everything SDK DLL 加载在 Lanwork 进程内，计入。

场景：固定数据为 5,000 个应用、10,000 条待办、1,000 篇约 2 KiB 的便签、20 个收纳分组共 1,000 条引用。预热搜索条，打开收纳标签，在搜索条里提交一次便签收集，并打开再关闭便签悬浮窗。然后收起全部窗口，连续采样 5 分钟。

| 项 | 目标 |
| --- | --- |
| 进程 Private Bytes 峰值 | ≤ 100 MiB，同时记录工作集 |
| 热召回 P95 | ≤ 100 ms |
| 应用、待办、便签结果 P95 | ≤ 50 ms |
| Everything 就绪时文件结果 P95 | ≤ 150 ms |
| Windows Search 回退时文件结果 P95 | 记录，不设目标 |
| 冷启动、首次索引 | 单独记录，不并入上面的 P95 |
| 收起后空闲 5 分钟 | 记录平均 CPU 和每秒唤醒次数 |
| 同时打开 5 个便签悬浮窗 | 单独记录 Private Bytes 增量 |
| 100 次呼出、查询、开关辅助窗口 | 记录 Private Bytes、USER、GDI 是否持续上升 |

口径：

- **热召回**：从进程收到热键消息，到搜索条第一次渲染完成（Slint `set_rendering_notifier` 的 `AfterRendering`）。不含 DWM 合成到屏幕的时间。
- **结果延迟**：从输入框文本变化（组合中的预编辑不算），到带同一查询序号的结果第一次渲染完成。文件结果包含 60ms 等待。被新输入取代的查询不计入样本，单独记数量。
- **样本**：每项至少 100 个有效样本，排除预热，保存原始时间戳。P95 取升序第 ⌈0.95 × N⌉ 个。Everything 和 Windows Search 分开统计。
- **每秒唤醒次数**：Lanwork 所有线程每秒上下文切换次数之和（性能计数器 `\Thread(lanwork*)\Context Switches/sec`）。
- 记录写明 release 或 debug、Slint 精确版本、渲染器、commit、机器、Windows build、GPU 与驱动、数据规模。
